# 性能优化：Agent 并行 + 查询缓存（路线 1）

> **历史文档标注（2026-08-30）**：本文记录 Dify 迁移下线前的实验与回归口径，属历史证据；当前财务查询走原生 SQL 链路（`tools/native_financial.py`），运行时已无 Dify 依赖。

> 日期：2026-08-30 ｜ 状态：已实现，待真实延迟对比


前端提问返回慢的主要来源（按链路拆解）：

1. **Agent 子任务串行**：`agents/langgraph_multi_agent.py::_run_subtasks` 用 for 循环串行执行 financial / research 子任务；自研 `agents/planner.py::execute` 同一轮多个 tool_call 也串行执行。串行最坏情况 = 两者耗时相加。
2. **Dify 财务查询重**：`quick_qa` 每次走 Dify HTTP 流式 + `generate_chart_image` 用 selenium 无头 Chrome 截图 PNG（数秒级），同一问题重复提问会完整重跑。
3. **RAG 链路无结果缓存**：同一问题重复提问会重新走「检索 → 表格聚合 → Rerank → 生成」，其中 `_parse_filters_with_llm`、Rerank、LLM 生成均为外部 API 调用。


- `agents/langgraph_multi_agent.py::_run_subtasks`：多任务时用 `ThreadPoolExecutor`（max_workers=4）并行执行 financial / research 子任务，耗时从「相加」变为「取最大」。
- `agents/planner.py::execute`：同一轮多个 tool_call 并行执行（顺序按结果原样回填 messages，保证 LLM 收到一致顺序）。
- 开关：`AGENT_PARALLEL_TOOLS`（默认 true，env 可关）。

- 新增 `utils/query_cache.py`：`SQLiteQueryCache`（表 `query_cache`，key/payload/expires_at）+ `make_cache_key()`（sha1）。
- **Dify 财务查询缓存**：`agents/planner.py::call_dify_chatflow` 按 `(user_id, question, PROMPT_VERSION)` 缓存 `{content, image, sql}`；命中时跳过 Dify + selenium 截图，并恢复 SQL 累积（`_append_sql` 加锁）。
- **前端 API 结果缓存**：`app/api.py` 的 `/chat` 与 `/chat/stream` 按 `(mode, user_id, question)` 缓存最终结果；流式命中时直接回放 content + meta + done。
- 开关：`QUERY_CACHE_ENABLED`（默认 true）、`QUERY_CACHE_DB`（默认 `database/query_cache.db`，已 gitignore）、`QUERY_CACHE_TTL`（默认 86400s = 24h）。

- `RAGPipeline.__init__` 新增 `_conversation_lock`，`call_dify_chatflow` 的 SQL 累积走 `_append_sql`（带锁），防止 Agent 并行写 `conversation_state.sql` 丢失/覆盖。


- 缓存的 SQL / 答案都是**历史上生成并验证过的**结果。做「修复后真实重跑」类回归（如改 prompt 后验证效果）时，必须：
  - 设 `QUERY_CACHE_ENABLED=false`，或
  - 清空缓存库：`python -c "from utils.query_cache import SQLiteQueryCache; SQLiteQueryCache('database/query_cache.db').clear()"`
- Dify 查询缓存 key 含 `PROMPT_VERSION`（`prompts/__init__.py`），改 prompts 后会自动换 key；但**改 Dify 工作流节点**不会自动换 key，需手动清库或设 TTL=0。
- SQL 回归证据（224/224、108/108）本身不受影响：同题命中缓存的 SQL 仍通过编译校验，但如需重新生成 SQL 请按上述方式关缓存。


- 单测：`tests/test_query_cache.py` 8 个用例（往返 / 未命中 / 过期 / TTL=0 / clear / 坏数据容错 / key 稳定性）。
- 全量：`python -m pytest tests/ -q` → **103 passed**（原 95 + 新增 8）。
- 导入冒烟：`RAGPipeline / AgentPlanner / LangGraphMultiAgentPlanner / call_dify_chatflow / SQLiteQueryCache` 均可导入。
- 语法：改动文件均通过 `ast.parse`。


环境：Docker 恢复 Dify 1.13 全家桶；MySQL(3306) 已入库医药股池数据（903 行/表）；
脚本 `tools/data_scripts/agent_latency_compare.py`（数据入库）与临时对照脚本；每题 `agent_query` 计时，

问题样例：`昭衍新药2024年全年净利润和营业收入分别是多少`（Agent 只调财务工具）。

| 口径 | P50 | P95 | 说明 |
| --- | --- | --- | --- |
| 串行首问（AGENT_PARALLEL_TOOLS=False） | 22.8s | 29.5s | Dify 工作流为主要耗时 |
| 并行首问（AGENT_PARALLEL_TOOLS=True） | 25.3s | 43.4s | 每轮只调 1 个工具，并行无收益 |
| 缓存命中（第二遍同题） | 7.5s | 22.8s | -67%；个别 21s 因 Agent 偶发改写查询致 miss |


问题样例：`昭衍新药2024年业绩变化的原因是什么`（需财务数据 + 研报归因）。

| 口径 | P50 | P95 | 说明 |
| --- | --- | --- | --- |
| 串行首问 | 79.2s | 99.7s | 财务 + 研报串行累加，真实痛点场景 |
| 并行首问 | 56.3s | 80.2s | -29%，收益取决于 Agent 是否同轮发多工具（不稳定） |
| 缓存命中 | 151.1s | 224.2s | 异常：Agent 改写查询→缓存 miss→重跑 Dify + 多轮 |

> 命中轮异常暴露自研 Agent 对归因题行为不稳（可能多轮/改写查询），是慢的深水区，
> 需靠 LangGraph multi-agent + 前端层缓存组合解决。


| 口径 | P50 | max | 说明 |
| --- | --- | --- | --- |
| 子任务串行（AGENT_PARALLEL_TOOLS=False） | 107.9s | 119.0s | financial/research 子任务串行 |
| 子任务并行（AGENT_PARALLEL_TOOLS=True） | 78.9s | 82.2s | **-27%，稳定收益** |

> supervisor 一次拆出 financial + research 子任务，`_run_subtasks` 并行后耗时取最大而非相加。


| 口径 | 耗时 | 说明 |
| --- | --- | --- |
| 首问 | 26.15s | 完整检索+精排+生成 |
| 缓存命中（同 user_id + question 第二遍） | 2.02s | **-92%**，内容与首问一致 |


1. **缓存是最大收益点**：前端层 -92%（用户重复问/追问直接受益）；Dify 层 -70%（Agent 原样传查询时）。
2. **并行对自研 Agent 单工具题无效**（每轮单工具）；对归因题收益 -29% 但波动大。
3. **归因混合题（80-120s）是真实痛点**，LangGraph multi-agent 子任务并行稳定 -27%；但 2026-08-30 切默认实测：multi-agent 每题 109-155s（supervisor+aggregator 额外 LLM 轮次 + 每题倾向拆 research），端到端反而不如自研 Agent 纯财务题（~23s）。**multi-agent 适合归因/复合题（结果更丰富），纯数据查询建议 handwritten 或按题型路由。**
4. **Dify 工作流本身 ~20-35s** 是单工具题主要耗时；迁移原生实现（路线 3）后可进一步压缩。


- 切换：`.env` 设 `AGENT_PLANNER_BACKEND=langgraph` + `AGENT_LANGGRAPH_MULTI_AGENT=true`（回退：设 handwritten）。
- 端到端：`/chat/stream` agent 模式归因题 89.8s，stage 序列 `parse → query_financial → search_reports → generate`，返回图表 + 20 条引用。
- SQL 证据链：multi-agent 子集 8 题（6 财务向），财务向题语句级通过率 **100%**（7/7 复核）；B2002/B2004 空 SQL 属意图模糊/开放性问题。
- 延迟：multi-agent 每题 109-155s，比自研 Agent 更慢（额外 LLM 轮次）；**结论见 5.5-3，建议按题型路由或纯数据场景回退。**


- 前端默认后端已切 LangGraph multi-agent（2026-08-30）；实测延迟不降反升，待评估：按问题类型路由（纯数据题走 handwritten、归因题走 multi-agent）或回退默认。

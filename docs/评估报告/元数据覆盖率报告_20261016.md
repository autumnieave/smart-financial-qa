# §3.2 元数据覆盖率报告（2026-10-16 / 修订 2026-10-17 · P1）

> **一句话**：`report_period` 从 **16.7% → 26.4%**（全库 chunk），其中**个股研报覆盖 63.1%**（目标 >60% ✅）；
> 但「全库 >60%」**按现在的语料不可达**——原因见 §二；`unit` **主瓶颈是语料**（**65.0% 的表里根本没写单位**，见 §六）；
> `metric_name` 表格块 **46% → 61.2%**；新增 `publish_year` **98.1%**（见 §七）。
> **本报告只改代码口径与测量，未重建索引** ⇒ 新字段/新覆盖率**尚未进库**。

## 一、口径与分母（先看这里，否则数字会被误读）

| 口径 | 定义 | 值 |
| :-- | :-- | --: |
| **全库 chunk** | 12,301 个 chunk（正文 6,443 / 表格 5,739 / 锅炉板 119） | — |
| **适用域：个股研报 chunk** | `doc_type == "stock"` 的 chunk（2,787 个） | — |
| **`report_period` 语义** | 「这篇研报是**对哪个报告期**的点评/跟踪」 | — |
| **`publish_year` 语义** | 「这篇研报**什么时候发布**」——行业研报（无报告期语义）的期间键 | — |
| **`unit` 语义** | 「这块内容用什么单位计价」——**只对表格块有意义**（正文块/锅炉板块天然为 0） | — |

**为什么必须分两个分母**：语料是 **160 篇个股研报 + 313 篇行业研报**，而行业研报的 chunk 占了 **77.3%（9,514/12,301）**。
行业研报是**市场研究 / 策略 / 周报**，本来就**没有「报告期」**（只有发布日期），给它硬赋报告期就是**造假元数据**。
所以「全库 >60%」这个目标在数学上要求**给行业研报也编报告期**——那不是覆盖率问题，是口径问题。

### 1.1 `unit` 覆盖率有三个分母（2026-10-17 补，防止误读）

| 口径 | 分子 | 分母 | 值 |
| :-- | --: | --: | --: |
| 全库 chunk | 1,623 | 12,301 | **13.2%** |
| 表格块 chunk | 1,623 | 5,739 | **28.3%** |
| 表级（解析器 `unit_candidates`，恰好 1 个候选） | 878 | 3,148 张表 | **27.9%** |

⇒ **13.2% 不是「语料里只有 13.2% 的表有单位」**——它的分母是**全部 chunk**，被 6,443 个正文块 + 119 个锅炉板块
（`unit` 对它们**永远为空**）稀释掉了。**`unit` 只在表格块上有意义**，比较时只看 **28.3%** 或表级的 **27.9%**。
三个数的分子/分母都不同，**不可互相除**；细节与第二个口径见 §六。

## 二、结论：全库 `report_period` >60% 不可达（三条理由）

1. **分母被行业研报主导**：行业 chunk 占 77.3%，若它们全部为空，全库覆盖率**上限 = 22.7%**（= 个股研报的 chunk 占比）。
   实测 26.4% 已经**吃到了个股研报的绝大部分 + 行业研报标题里显式带期的部分**。
2. **个股研报本身也有「无报告期」的类型**：首次覆盖 / 深度报告 / 事件点评（如「BD 进入收获期」「OTC 稳健增长」）
   通篇不绑定某个报告期。个股研报里 36.9% 的 chunk 属于这类。⇒ **63.1% 已接近这一层的上限**。
3. **要凑到 60% 只剩一条路：把行业研报正文里顺带提及的季度当报告期**。实测这条路能到 **36.4%**，
   但 **1,227 个行业 chunk** 的报告期来自「顺带提及」，样例（对照实验实测）：

| 推出来的报告期 | 研报标题 | 判定 |
| :-- | :-- | :-- |
| `2025Q2` | 医药健康行业研究：创新药龙头BD频出，关注慢病&小核酸赛道 | ✗ 顺带提及 |
| `2024Q4` | 医药生物周报：海外制药及医疗器械企业 JPM大会业务进展更新 | ✗ 顺带提及 |
| `2024Q4` | 医药健康行业研究：药店、中药2026年度策略：蛰伏蓄势，以候风至 | ✗ 与标题策略年度矛盾 |
| `2025Q3` | 2026年医药行业投资策略：聚焦创新、出海与确定性 | ✗ 把复盘季度当报告期 |
| `2025H1` | 2025年中期医药生物行业投资策略报告：BD催化创新药资产价值重估 | ✓ 合理 |

⇒ **假阳性占比高（约 4/5）**，且这些错值会**污染 L5-C 期间过滤**（把「2025Q3 问句」路由到一篇策略报告）。
**决策：正文首段推断只对个股研报启用**（`BODY_PERIOD_DOC_TYPES = ("stock",)`），行业研报只认**标题里的强期词**。

## 六、`unit` 为什么只有 13.2% / 28.3%（两个口径）

### 6.1 表级口径（主口径，分母 = **入库表数 3,148**，用解析器的 `unit_candidates`）

> **分母核对（2026-10-17）**：原始扫描 **3,343** 张 → 剥尾部锅炉板后 **3,148** 张，差 **195 张**，涉及 **143 篇**。
> 被剔除的都是**免责声明区**里的表（评级说明、销售联系方式、免责条款），样例：`公司评级 / 买入…`（8×2）、
> `上海 | 蒋诗烽 | 总经理助理、销售总监 | 021-68415309`（24×6）。它们**本就不入库**（`strip_boilerplate=True`），
> 因此 65% 的分母用 **3,148**，与 `compare_table_parse` 的 3,343 不矛盾。

| 项 | 表数 | 占全部表（3,148） |
| :-- | --: | --: |
| **零候选：表里根本没写单位** | **2,047** | **65.0%** |
| 恰好 1 个：可提取（解析器必然写入 `unit`） | 878 | **27.9%** |
| **多单位：按「不猜」策略置 `None`** | **223** | **7.1%** |

⇒ **主瓶颈是语料本身**：**65.0% 的表里一个单位都没写**，无从提取；剩下 7.1% 是**一张表混用多个单位**（`万元` + `元`），
按既有策略**不猜、置 `None`**。**可提取的都提取了**（878 张 → 对应 chunk 上 `unit` 全部非空）。

### 6.2 chunk 级独立正则扫描（次要口径，分母 = 5,739 个表格块）

对表格块**渲染文本**（表标题 + 行）做「表内任意位置是否出现单位标注」的扫描：

| 项 | 块数 | 占表格块 |
| :-- | --: | --: |
| 已填写 `unit` | **1,623** | **28.3%** |
| 扫到单位标注（独立正则） | 1,849 | 32.2% |
| 其中多单位 | 299 | 5.2% |
| **一个单位都没扫到** | 3,890 | **67.8%** |
| 已填 / 扫到 = 1,623 / 1,849 | — | **87.8%** |

⚠️ **这个口径与 6.1 不可互相除**：6.2 扫的是**渲染后文本**（可能含切片后仍在的正则命中），
解析器走的是 `head_text or first_column or body_text` 的**短路**（命中即停），
所以 6.2 的「扫到」是**乐观上界**，而 6.1 才是「解析器真正拿到候选」的口径。
**引用数字时请用 6.1（表级）**；6.2 只用于回答「是不是漏提取了」。

### 6.3 结论

**不是「提取率不够」，而是「语料没写单位」**。再往上提只剩两条路，都已裁决：

- **多单位取众数**：+223 张表，但会改「不猜」策略 ⇒ **2026-10-17 裁决：不做**；
- **从上下文猜单位**（如全篇都是「万元」就默认）：**未做**（会污染 L1 数值核验的换算链）。

**（d）已知正则缺陷（登记，未改）**

1. 裸 `百万元` / 表头后缀 `亿元` / `人民币万元`（无括号、无「单位：」）—— **+62 张（3.0%）**；

4. `单位 万元`（无冒号）不命中。

## 七、决策与生效条件（2026-10-17）

**决策 A（`unit` 多单位）：不做取众数。** 违反「不猜」原则；`unit` 不参与检索排序、对 L5 无影响。

**决策 B（`publish_year`）：做。** 已落地为**补充字段**（不替代 `report_period`）；L5-C 期间过滤**按 `doc_type` 选键**——
个股研报用 `report_period`、行业研报用 `publish_year`（`src/filters/period_gate.py`，默认不启用）。

   仍是**旧口径（`report_period` 16.7%、无 `publish_year`）**。重建 ≈ **7 分钟 + 嵌入 API 配额**（上次实测 423.5s）。

# 生成慢归因（2026-10-23）

## 结论

- **生成慢的主因是输出 token 量叠加供应商吞吐，不是 thinking，也不是重试。**
- 10 条有效 `/chat` 请求中，`generate_ms` 与 `completion_tokens` 的 Pearson 相关系数为 **0.95**；与 `prompt_tokens` 为 **-0.207**。
- 样本平均生成吞吐 **46.2 tok/s**（逐题 27.6–59.3 tok/s），平均 completion **1,305 tokens**。
- `AGENT_ENABLE_THINKING=false` 已生效；`src/llm/generator.py` 还硬编码了 `extra_body={"enable_thinking": False}`。
- `MAX_RETRIES=3`，但样本内无 429 / timeout / 重试日志，错误数为 0；不是重试放大耗时。
- 因此，**不能把 59.1s P95 归因于“上下文太长”**。Prompt 很长（均值 29,191 tokens，最大 78,989）主要推高 token 成本和 prefill 成本，但本样本中最大 prompt 题并非最慢题。

> 这是单机、顺序、10 题的小样本相关性分析，不是因果实验，也不能外推线上并发 P99。

## 一、样本与口径

| 项 | 取值 |
| --- | --- |
| 原始日志 | `训练结果数据/logs/step1_20261023/20261023.jsonl` |
| 有效样本 | 10 条 `/chat`；另 1 条 `/health` 已排除 |
| 模式 | `rag`，非流式 `/chat` |
| 模型 | `qwen3.5-plus` |
| 查询缓存 | 关闭，10 条均 `cache_hit=false` |
| 运行方式 | 单机、顺序、单并发 |
| 生成段 P95 | **40.0s** |
| 端到端 P95 | **59.1s** |

`generate_ms` 是生成器内部计时；日志中的 `generate_wait_overhead_ms` 最大仅 **1.063ms**，说明 40s 级耗时不是 wrapper 等待或事件循环阻塞造成的。

## 二、关键统计

| 指标 | 结果 |
| --- | ---: |
| `corr(generate_ms, completion_tokens)` | **0.95** |
| `corr(generate_ms, prompt_tokens)` | **-0.207** |
| 平均吞吐 | **46.2 tok/s** |
| 吞吐范围 | 27.6–59.3 tok/s |
| 平均 prompt tokens | 29,191 |
| 平均 completion tokens | 1,305 |
| completion 触顶 2,048 | 1 题（`B2007|2`，35.35s） |
| 样本错误 / 重试 | 0 / 0 |

### 代表性对照

| 题号 | prompt_tokens | completion_tokens | generate_ms | 吞吐 |
| --- | ---: | ---: | ---: | ---: |
| `B2002|1` | 6,244 | 1,918 | 40,214 | 47.7 tok/s |
| `B2003|2` | **78,989** | 742 | 14,690 | 50.5 tok/s |
| `B2007|2` | 73,583 | **2,048（触顶）** | 35,353 | 57.9 tok/s |
| `B2077|1` | 5,060 | 1,225 | 29,208 | 41.9 tok/s |

`B2002|1` 的 prompt 只有 6,244，却生成 40.2s；`B2003|2` 的 prompt 最长（78,989），生成只有 14.7s。可见在本样本里，**输出长度比输入长度更能解释生成耗时**。

## 三、排除项

| 假设 | 检查结果 | 判断 |
| --- | --- | --- |
| thinking 没关 | 运行时 `AGENT_ENABLE_THINKING=False`；生成器硬编码 `enable_thinking=False` | **排除** |
| 重试放大 | `MAX_RETRIES=3`；样本无 429 / timeout / 重试日志，`error=null` | **排除** |
| 事件循环阻塞 | `generate_wait_overhead_ms` 最大 1.063ms | **排除** |
| 上下文太长是主因 | prompt 与 generate_ms 负相关；最大 prompt 题不是最慢题 | **本样本不成立** |
| 输出太长 / 吞吐不足 | completion 与 generate_ms 相关 0.95；均值 46.2 tok/s | **主因** |

> 注：`20261023.jsonl` 汇总文件中另有 429 记录，来自 API 鉴权/限流探针；本报告只统计 `step1_20261023/20261023.jsonl` 的 10 条业务请求。两类记录不混用。

## 四、优化方向

1. **流式首字（TTFT）**：总生成时间不变，但用户感知从“等完整答案”变成“先看到首字”；需要给 `/chat/stream` 单独埋点，当前未测。
2. **缩短输出**：限制结论长度、减少重复解释、按问题类型选择答案模板；本样本已有 1 题触顶 2,048 tokens。
3. **上下文压缩**：对 2.9 万平均 prompt 做去重/摘要/只保留证据行，主要降低 token 成本和 prefill，不应承诺单独把 P95 降到秒级。
4. **模型路由**：简单事实题走更快模型，复杂归因题保留 `qwen3.5-plus`；需要单独评测质量退化。
5. **不把“低延迟”写进简历**：当前可写的是“结构化日志定位生成段为瓶颈”，不是“已实现低延迟”。

## 五、边界

- n=10，单次运行，单机顺序；相关系数只说明样本内方向，不是因果结论。
- `generate_ms` 是供应商调用总耗时，未拆分首 token 延迟、decode 速度和网络排队。
- P95 是 10 个点的线性插值，不稳定，不能作为线上 SLA。
- 当前 `/chat` 等完整答案返回；流式用户感知延迟（TTFT）尚未测量。
- 成本单价未登记，本报告只分析 token，不计算金额。

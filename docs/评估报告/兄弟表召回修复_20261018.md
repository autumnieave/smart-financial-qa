## 二、实现

### 2.1 索引

`MultiStageRetriever` 在表级 BM25 文档上新增两个倒排：

- `file_path → [doc_index]`：同一篇研报的全部表；
- `table_id → doc`：按表 ID 直接取整表 payload。

BM25 文档本身已按 `table_id` 合并全部切片，带 `content`、`metric_names`、`anchor_cells`、`table_type`、`stock_name` 等字段，因此兄弟表召回不需要额外查 Qdrant。

### 2.2 触发条件

只有以下条件全部满足才触发：

1. `SIBLING_TABLE_RECALL_ENABLED=true`（默认 `false`）；
2. 查询能抽出指标（如“营业收入”）和公司实体（如“桂林三金”）；
3. 某个已选中的同主体文件中，所有已选表都不覆盖查询的 **指标 / 期间 / 单位**；
4. 同文件存在满足硬约束的兄弟表。

期间口径：

- 有明确报告期时用 `2025Q3 / 2025H1 / 2024A` 硬匹配；
- 研报预测题额外识别 `2025年...预计` → `2025E`；
- 单位只做字面同口径匹配（`百万元` 不会匹配 `%`，也不做换算）。

### 2.3 替换规则

- **不追加**：从最终 top-k 里选最低排名的表替换，保持 `len(output) == k`；
- 优先替换“其他文件”的最低排名表，避免把同文件已有证据挤掉；
- 同一张表不重复插入；
- 结果 payload 标记 `sibling_recall=True` 与 `sibling_score`，trace 记录：
  `sibling_recall_enabled / sibling_candidates / sibling_replaced / sibling_files / sibling_table_ids`。

### 2.4 与实体定向重试的衔接

AEXP|03/04 的金标文件是在 `retry_entity` 合并后才进入 top-10 的，因此兄弟表召回在两处执行：

1. `retrieve()` 首轮 top-k 之后；
2. `retrieve_with_iteration()` 合并实体定向重试结果之后。

第二处是本次修复的关键；只放在首轮会漏掉“实体重试才带回同文件 `#t1`”的场景。

## 四、边界与已知问题

1. **只做同文件兄弟表。** AEXP|02/07/08 的金标文件在向量 top-100 / BM25 top-60 / 最终 top-50 全部缺席，兄弟表召回无法触发；需要报告级召回或查询改写，属于结构性改动。
2. **AEXP|08 是反例。** 开启后同主体另一篇研报的 `#t2` 被召回，但金标表仍未进入 top-10；说明兄弟表召回不能替代报告级召回。
3. **多篇同主体研报会一起补表。** AEXP|03 补了 3 个同主体文件的预测表，AEXP|04 补了 2 个；答案会并列比较不同研报的预测值（如 2,307 vs 2,308、730 vs 656），这是证据充分后的正常行为，但需要在产品展示层标明报告时点。
4. **依赖 BM25 文档元数据。** 若表级 BM25 文档缺 `file_path` / `metric_names` / `anchor_cells`，兄弟表召回直接 no-op；不静默猜测。
5. **线上仍未默认启用。** `SIBLING_TABLE_RECALL_ENABLED=false`，且 `MULTI_STAGE_RETRIEVAL_ENABLED=false`；本修复是评测 / 实验口径，不改变线上默认链路。

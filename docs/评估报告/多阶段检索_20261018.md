## 二、阶段 3 的设计与边界

### 2.1 三段式

1. **表级粗召回**：只查 `chunk_type=table`，避免 169,242 条 row_fact 淹没 5,739 个表切片（约 **29.5:1**）。
2. **行级精定位**：只查 `chunk_type=row_fact`，并用候选 `table_id` 做硬过滤；行分只用于候选表排序，不直接作为最终返回单元。
3. **整表返回**：按 `table_id` scroll 全部表切片，按 `table_slice_index` 拼接；一条结果 = 一张表，`row_hits` 作为证据字段。

诊断模式 `row_first` 只用于归因，不作为默认路径。所有中间计数写入 `MultiStageTrace`：
`coarse_hits / coarse_tables / row_hits / row_tables / selected_tables / timings_ms`。

### 2.2 本报告不混淆的三件事

- **表级召回收益**（同主体 / 真内容）≠ **行证据正确性**（指标+期间是否对上）。
- **30 题 L5 旧标注**是正文 chunk 标注，不是表级 gold；表路只返回整表，不能拿它做相同分母的 HR/nDCG/MRR。
- **单阶段 vs 多阶段**在 v5 上对比；不能把 v5 的 table-level 数字直接和旧 v3 的 chunk-level 4.93 对比。

## 三、三个确认项

### 3.1 Q1：169,242 条 row_fact 的构成

| table_type | row_fact | 物理表数 | 条/表 |
| --- | ---: | ---: | ---: |
| financial_statement | 64,886 | 597 | 108.7 |
| forecast | 38,869 | 531 | 73.2 |
| ranking | 45,380 | 542 | 83.7 |
| industry_summary | 15,568 | 633 | 24.6 |
| valuation | 4,539 | 202 | 22.5 |
| pipeline | 0 | 492 | 0 |
| other | 0 | 151 | 0 |
| **合计** | **169,242** | **3,148** | **53.8** |

三个分母都成立但含义不同：
- `169,242 / 3,148 = 53.8`：分母含 643 张 0 事实的 pipeline/other；
- `169,242 / 2,505 = 67.6`：只算真正生成事实的 5 类表；
- `169,242 / 5,739 = 29.5`：按表 chunk（切片）算，也是本阶段最重要的稀释比。

**确认：只覆盖 5 类数值表，无越界。**

### 3.2 Q2：行级 unit 70.3% —— 更正

Qdrant 的 `unit_source` 计数：

| unit_source | row_fact |
| --- | ---: |
| cell | 119,017 |
| header / caption / footnote / table / multi | 0 |
| none | 50,225 |

**但不能把这个 70.3% 直接写成“每个目标单元格自身都带单位”。** 代码路径是：
- 先看 `metric_cell + header + metric + value`；
- 再看 caption/title；
- 再看 footnote；
- 都没有时回退到 `table.unit`，并沿用 `table.unit_source`。

因此 `unit_source=cell` 可能来自**表级单位回退**，不是目标单元格自身。实测反例：

```text
马应龙(600993)｜盈利预测与估值(人民币)｜市盈率(P/E) > 2025E: 17.62 百万元
```

P/E 不应是“百万元”。这说明多单位表的行级单位存在**语义错配**。

**结论更正**：
- “caption/footnote 回退贡献 0”仍然成立（计数为 0）；
- “70.3% 全部来自单元格自身”**不成立**；
- 行级 unit 与表级 28.3% 的差异，既来自单元格显式 `%` / `元/股`，也来自表级单位回退；
- 这是阶段 2 遗留的数据质量问题；**2026-10-18 已修并重建 v6**，详见 §十。

## 四、27 + 4 实体题结果（v5 修复前基线）

口径：同一 query vector；实体闸门 `min_keep=0 + keep_unknown_entity=True`；整表精排 20 条 → 每文件≤2 → top-10。

| 模式 | top10 同主体 | 其中真内容 | 裸表行 | 碎片 | 正文提及 | 有行证据题数 | 空上下文 | trace P95 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |

**重要：行证据覆盖不等于行证据正确。** 4 条严重题的抽检结果：

| 题号 | top-10 行证据条数 | 指标命中 | 指标+期间同时命中 | 命中表数 |
| --- | ---: | ---: | ---: | ---: |
| B2065 | 21 | 0 | 0 | 0 |

根因有三类：
1. **季度粒度缺失**：研报表多为年度/预测表，2025Q3 的实际值本来就不在表里；这类问题应由 SQL 路回答。
2. **指标词未硬匹配**：`利润总额`、`研发费用` 等行事实排在候选里，但 `row_hits` 里混入股息率、营业成本、市值等行。
3. **期间标签不是问题里的期间**：`2025Q3` 查询命中 `2025E/2024A` 行，说明行级打分只做了语义相似，没有期间约束。

### 4.2 空上下文

- single 8 题、table_first 5 题。空上下文全部来自**实体闸门把 20 条候选全过滤**（gate `0/20 → 保留 0`）。
- table_first 的 5 题是：B2063 达仁堂、B2070 陇神戎发、B2072 新天药业、B2074 广誉远、B2076 振东制药；全部为实体闸门 `0/20 → 保留 0`。
- 归因要分开写：B2070 / B2072 / B2076 属 B-58 已归因的语料缺口（无专属个股研报）；B2063 / B2074 属稀疏覆盖，不是“7 家语料缺口”中的同一类。
- B2003 华润三九、B2012 太极集团、B2062 奇正藏药被多阶段救回（single 空 → table_first 非空）。
- 线上默认 `ENTITY_GATE_ENABLED=false`；若上线，必须保留 `keep_unknown_entity=True + min_keep>0` 的安全垫。

## 五、30 题 L5：两个口径，必须分开

### 5.1 table-level 打分：不可用

用旧正文 chunk 标注直接给“只返回整表”的表路打分，single/table_first 都是 **HR@10=0、nDCG@10=0、MRR=0**（56 个相关片段全部未命中）。  
**这不是多阶段的效果结论**，而是返回单元不匹配：旧标注是正文 chunk，表路只返回表，二者没有可比性。结果保留在 `l5.json` 作为口径反证。

### 5.2 全索引 chunk-level 回归：row_fact 必须隔离

同口径：向量-only（`HandwrittenRetriever` K=50 → qwen3-rerank 20 → 每文件≤2 → top-10）；不是混合检索。

| 配置 | 点数 | HR@10 | P@10 | nDCG@10 | MRR | 命中/相关 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| v3_structured | 12,301 | **0.0656** | 0.0367 | **0.1002** | **0.0942** | 11/56 |
| v5_all | 181,543 | 0.0267 | 0.0233 | 0.0512 | 0.0442 | 6/56 |
| v5_no_rowfacts | 181,543 | **0.0656** | 0.0367 | **0.1002** | **0.0942** | 11/56 |

**结论：row_fact 混入普通召回会让 HR@10 掉 59%、nDCG 掉 49%；排除后与 v3_structured 完全相同。**  
⇒ 多阶段的 `chunk_type` 隔离不是优化项，而是 row_fact 能存在的前提。

> 未完成项：全索引 **HybridRetriever（含 BM25）** 在 181K 点上构建 BM25 时进程被内存压垮，未产出结果；本表是向量-only，不能冒充混合检索基线。

## 六、延迟

方法：30 条 query embedding 缓存；每题 5 次，丢弃 warm-up；Qdrant `query_points` top-50；无 rerank。

| 配置 | 点数 | P50 | P95 | P99 | mean |
| --- | ---: | ---: | ---: | ---: | ---: |
| v3_structured 全量 | 12,301 | 23.85ms | 56.15ms | 173.48ms | 31.22ms |
| v5 全量 | 181,543 | 24.59ms | **517.13ms** | 982.62ms | 85.42ms |
| v5 仅 table | 181,543 | 25.47ms | **43.01ms** | 73.07ms | 27.85ms |

**解读**：181K 全量搜索的 P95 是 12K 的 9.2 倍；加 `chunk_type=table` 后反而略优于 12K。  
这支持“多阶段只查表/只查行事实”的设计，也意味着任何把 row_fact 放进普通召回的方案都会同时付出质量和延迟代价。

## 七、判定与下一步

### 7.1 本阶段能下的结论

1. **表级粗召回 + 整表返回成立**：同主体、真内容、空上下文三项均改善。
2. **行级精定位只完成“覆盖率”，没有完成“正确率”**：当前不能把 `row_hits` 当证据对外展示。
3. **row_fact 必须与普通召回隔离**：全索引对照给出了同口径证据。
4. **Q3/季度题不应由表路硬扛**：研报表以年度/预测为主，季度实际值应走 SQL 路；这也是答案层“研报预测混入指标题”的根因之一。

### 7.2 决策

- **不切线上默认路径**；`MultiStageRetriever` 保留为实验实现。
- `research_reports_v5_rowfacts` 保留为修复前基线；修复实验使用 `research_reports_v6_rowfacts`，见 §十。
- 下一轮优先级：
  1. **路由**：先判定“表题 / 正文题 / SQL 题 / 混合题”，再决定走哪条召回；不要把三种 chunk 混在一个 top-50 里。
  2. **行定位正确性**：指标词 + 期间硬约束已完成第一版（§十）；仍需 30 条表级 gold 验证正确率。
  3. **表级 L5 gold**：当前旧标注无法评价整表返回，必须重新标注“表级相关”。
  4. **阶段 2 单位修复**：已完成并重建 v6（§十）。

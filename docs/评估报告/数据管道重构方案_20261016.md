# 数据管道重构方案：表格结构化（2026-10-16）

> 结论一句话：**索引里 87.5% 的 chunk 是「一行一 chunk」的表格行（平均 83.7 字，且只来自 449 张表）**——
> 这是 B-58「稀疏覆盖」、B-59「精排劫持」、引用碎片化的**共同上游**。把它们按「一张表一个 chunk」重建，
> 索引可从 **57,031 点降到约 7,600 点（-87%）**，同时让数值可溯源到单元格、让过滤器读元数据而不是猜正则。
>
> 本方案只写方案，未动代码；执行前需按 §七 逐步确认。
>
> **执行进展**：§八 逐节记录实测与口径更正；**§8.8（2026-10-16）为最终状态** —— 元数据补全 + 重建 `v3_structured`（12,301 点）+ 复评 L5 已完成。

## 一、为什么重构

现有管道的根问题不是「检索/精排调参」，而是**语料形态**：把表格按行拆成独立 chunk，导致

1. 索引被「没有任何可回答内容」的碎片占满（86% 的 chunk <200 字）；
2. 「公司名 + 一串数字」这种与「公司 + 指标」查询词面高度重合的碎片，在精排里**系统性击败真正的分析正文**；
3. 数值与它的**行列语义**（这是哪张表、哪一列、哪一个报告期、单位是什么）在切分时就丢了，事后无法还原。

候选层打补丁（L5-B 实体硬闸门、B-59 A 裸表行闸门）能救回一部分（见 §五 收益 2），
但只能一个个规则地打地鼠 —— **根治必须改数据管道**。

## 二、证据（四条核心 + 一条支撑）

### E1｜表格行占绝对多数，且极端碎片化（`训练结果数据/l5b_measure/table_structure_scan.json`）

| 项 | 值 |
| :-- | --: |
| 集合总 chunk（`research_reports_v3_l5a`） | 57,031 |
| 其中**表格行** chunk（`is_table_row=True`） | **49,913（87.5%）** |
| 文本块 chunk | 7,118（12.5%） |
| 这些表格行**来自多少张表**（去重 `parent_id`） | **仅 449 张**（⚠️ 口径更正：449 是「有表格的文档数」，真实表数 **3,343**，见 §八） |
| 表格行平均长度 / p50 / p90 | 83.7 字 / 74 字 / 136 字 |
| 全库 <200 字 / <100 字 chunk（`v3_full`） | 49,025（86%）/ 34,045（60%） |

⇒ 平均**一张表被拆成 111 个 chunk**，每个 74 字左右。

### E2｜行碎片劫持最终 top-10（`docs/评估报告/B-59_精排丢弃4条_人工复核工作单_20261016.md`）

- 4 道「公司 + 财务指标」题的 top-10 里，**36/40 条**是行业周报夹带的个股筛选表行；全库此类 chunk 仅 **864 条（1.5%）**。
- 劫持样本原文（B2065 top-1，精排 0.6988）：

  ```
  300181. SZ  佐力药业  0.72  2.73  3.71  5.08  2.53  130.81      # 54 字
  证券代码: 300181.SZ; 证券简称: 佐力药业; 待分配利润(2023年报): 7; …  # 135 字
  ```
- 人工复核结论：**4 题 top-10 对「所问指标」确实不相关**；A 闸门排除表行后，3/4 题的「同主体真内容」从 0 恢复到池内上限（8/7/6 条）。

### E3｜正文块被样板稀释

公司研报 chunk 头部固定夹带 300~500 字样板：`[TABLE_PLACEHOLDER_106]`、**表格说明**、分析师/执业编号/邮箱、
相关报告、免责声明；真实内容（事件/点评/分析）在**后段**。实测 774 字的 chunk 里 774 字全是「证券研究报告/公司研究/
分析师/地址/表格说明」，正文另起 —— 相关性被稀释，也让精排的长文本打分失真。

### E4｜结构化信息**已经存在**，只是没有用起来

`v3_l5a` 的表格行 chunk 已带元数据：`is_table_row` / `row_index` / `parent_id` / `stockCode` / `stockName` /
`chunk_index` / `chunk_total`。也就是说**结构化不需要从零开始**，缺的只有三件：

1. **表格要成块**（现在是「一行一 chunk」）；
2. **指标语义**（列名 → `metric_name`、单位归一、报告期）；
3. **正文/表格/样板三类要可分**（`chunk_type`）。

### E5｜（支撑）数学标记污染数值

MinerU/LaTeX 残留：`同比 $+32.81\%$`、`$3 2 . 8 1 \%$`、`$\bullet$`、`$6 7 \%$` —— 数字被空格与 `$` 切断，
导致数字抽取必须先清洗；单元格与数字的对应关系在文本化时丢失。L1「引用文本数字命中 99.7%」里剩下的 0.3% 与此相关。

## 三、改造内容（4 步）

### 3.1 `splitter.py`：表格解析为结构化对象，**一张表一个 chunk**

- 新增 `Table` 结构：`{table_id, source_file, title, caption, headers, rows, unit, stock_codes, report_period, page}`；
- 序列化：**Markdown 表**（带表头与单位）作为 chunk 正文；原始结构化数据存 payload（`table_json` / `row_index_map`，超长截断）；
- 超长表（如 111 行）按「**表头重复 + 每 K 行**」切片，保留行列语义；
- 正文块**剥离** `[TABLE_PLACEHOLDER_*]` 与「表格说明」，其内容移入对应表的 `caption` 字段；
- 保留 `parent_id` 兼容父表回拉（`TABLE_AGG_TOPK`），`is_table_row` 语义改为 `chunk_type=table`。

### 3.2 元数据补全（每 chunk）

| 字段 | 含义 | 来源 |
| :-- | :-- | :-- |
| `chunk_type` | `prose` / `table` / `caption` / `boilerplate` | 切分器判定；`boilerplate`（免责声明/分析师/相关报告）默认不进候选 |
| `stock_code` / `stock_name` | 表级主体 | 表内出现的代码 + 文件名/表头 |
| `report_period` | `2025Q3` / `2024年报` … | 文件标题 + 正文正则白名单 |
| `metric_name` | 列名归一（营业收入/归母净利润/毛利率/研发费用…） | 表头 + 指标词表（沿用 `filters.row_gate.METRIC_TERMS`） |
| `unit` | 万元/百万元/亿元 → **元** | 表头括号单位 |
| `row_index` / `table_id` | 行级定位 | 表内序号 |

## 八、口径更正（2026-10-16 · 第一步实测）

> 本节为**追加**说明。上文 §二 / §三 的原始数字**不改写**（保留方案定稿时的记录）。

### 8.1 「449 张表」是测量失误 → 实际 **3,343 张表**

- §二 E1 的「去重 `parent_id` = 仅 449 张」中，legacy 口径的 `parent_id = f"{filename}_tables"`
  是**一篇文档一个**（不是一张表一个），故 449 实为「**有表格的文档数**」。
- 用 `table_struct.scan_tables` 重新枚举：473 篇 → **3,343 张表（7.4 倍）**，共 58,814 数据行。
- **第二个实测事实**：3,343 张表里 **0 张带 `<th>`**（表格由 PDF 解析器生成，表头同样是 `<td>`）
  ⇒「有没有表头」**不能靠 `<th>` 判定**，必须按结构推断。已实现并单测覆盖的四条规则：

| # | 原文结构 | 判定 |
| --: | :-- | :-- |
| 1 | 带 `<th>` | 首行即表头 |
| 2 | **跨满列的单格标题行**（`<td colspan="6">盈利预测与估值</td>`） | 该行移入 `caption`，**下一行**才是表头 |
| 3 | **2 列表 = 键值卡片**（`总市值（百万元） \| 11,349.65`） | **无表头行**，按 `键: 值` 序列化（按规则 4 会**吃掉首行数据**） |
| 4 | 其余（`会计年度 \| 2024 \| 2025E \| …`） | 首行即表头 |

- 实测占比：`has_header` **89.3%**（2,984 张）/ `is_key_value` **10.5%**（351 张）。

### 8.6 语义维度与结构分（2026-10-16 完成 · 第 4 步）

**本节取代 §8.5 末尾「下一步」那条，并更正它的一处预期**（原文不改写）。

**一、解析器侧（`src/data/table_struct.py`）**：`Table` 新增三个字段，并进入 `to_payload()`（→ chunk metadata）：

| 字段 | 含义 | `to_payload` 键 |
| :-- | :-- | :-- |
| `section_rows` | **全宽标签行**（`利润表` / `成长能力` / `备注:…` / `资料来源：…`）在 `rows` 中的下标 | `table_section_rows` |
| `sub_header_rows` | **次级表头行**（跨子表重复表头 / 多级表头） | `table_sub_header_rows` |
| `merged_cells` | 合并单元格 `{row, col, rowspan, colspan}`（`rows` 坐标；表头行自带的合并不输出） | `table_merged_cells` |

判定按**可靠性排序**：① 结构信号（源 `<td colspan == 列宽>` 独占整行，精确）→ ② 整行只剩 1 个非空格（兜底）
→ ③ 各列文本全同（兜底，Markdown 表格用）。**修掉三个真漏判**：①「分节行后面必须有数据行」漏掉表格末尾的
`备注` / `资料来源` 行（全库 40 处）；②「单非空格必须在首列」漏掉源把标签写在中间 `<td>` 的行；
③ 没用 `colspan` 事实，漏掉 2 列表 / 末行 / 「近满宽」三类。

**二、Gold 侧（`训练结果数据/gold_set/annotate_gold_struct.py`）**：三个字段**全部由源 HTML 事实推导**
（`colspan` / `rowspan` / 表头空格位置），**不调用**解析器的检测启发式，避免「拿判定当标准答案」。
- 该脚本自身被抓出一处 bug：合并单元格的**列号要按 HTML 占位语义算**（上方 `rowspan` 未走完的列要跳过）
  ——NO=16 的 `公司评级` 单元格在源行里是第 1 个 `<td>`，但落在**列 1**。
  **是结构分先跑出 `merged_cells` F1 = 0.9667 才暴露的**，说明该指标有判定力。

**三、结构分（`src/tools/data_scripts/table_teds.py`）**：`structure_score` = 三维度 F1 的**宏平均**；
`combined = teds × structure_score`。TEDS 口径不动（已冻结），结构分独立成指标。

| 项 | 结果 |
| :-- | :-- |
| Gold 平均 TEDS / 结构分 / 综合分 | **1.000000 / 1.000000 / 1.000000** |
| 各维度平均 F1 | `section_rows` 1.0 · `sub_header_rows` 1.0 · `merged_cells` 1.0 |
| 判定力（注入破坏单测 9 例，`tests/test_table_teds.py`） | 丢分节行 / 多分节行 / 合并几何错 / 丢次级表头 → **< 1.0**；TEDS 满分但结构丢失时**综合分仍 < 1** |

> ⚠️ **交底：与 §8.5 的预期不符。** §8.5 写「加语义维度后 TEDS 满分不再可能」——**实测不是这样**。
> 这 10 张表上，解析器的语义标注与源 HTML 事实**逐项一致**（结构分 1.0）。原因是解析器本来就在读
> `colspan` / `rowspan` 属性，而 §8.5 列的三条「语义缺口」是**未记录**，不是**记错**。
> 所以真实结论是：**结构分把「结构是否被保留」从假设变成了实测，实测结论是「这 10 张全对」**；
> 要看到缺口得看全库口径（下节）。

**四、全库客观校验**（`src/tools/data_scripts/measure_section_rows.py`；2,990 张 HTML 表 / 995 条源事实）

| 口径 | TP | FP | FN | P | R | F1 |
| :-- | --: | --: | --: | --: | --: | --: |
| **GT-strict**（满宽 = `sum(colspan) == 列宽`）——**采用** | 993 | 15 | 2 | **0.9851** | **0.9980** | **0.9915** |
| GT-v2（近满宽 = `>= 列宽 - 1`）——**不采用** | 1003 | 5 | 154 | 0.9950 | 0.8669 | 0.9266 |

（GT-v2 的 recall 掉到 87%，是因为放宽后混进大量「单值落在中间列」的伪标签行，故采用 GT-strict。）

残差 17 条**逐条看过**，两类的**口径都比解析器弱**：

**边界**：`merged_cells` 两侧同源于 `colspan` / `rowspan` 属性，一致是**构造性**的——它是
**回归护栏**（防将来改动丢结构），**不是准确率测量**；真正靠启发式的只有 `section_rows`
（上表即为它的实测精度）。`section_rows` 等是**表内绝对行号**，一表切多 chunk 时坐标不随 `row_start` 平移，
下游按表取数即可。

#### 8.8.4 重建暴露并修掉的两个真 bug（关键）

`text-embedding-v2` 单条 **≤ 2048 token**。一表一 chunk 后预检发现 **702 块 > 2048 字、最长 13,239 字** ⇒
API 报 `Range of input length should be [1, 2048]`，重试 3 次后抛 `RuntimeError`（正文本体安全：最大 1,194 字、p99 1,025 字）。
修法两层：

1. `src/data/table_struct.py`：新增 **`slice_ranges(max_rows, max_chars)`** —— 二分找「渲染长度 ≤ 上限」的最大行数，
   **单行自身超限仍单独成片（不丢行）**；`to_slices()` 改按该区间切片（`TABLE_SLICE_MAX_CHARS = 1200`）；
2. `src/embeddings/client.py`：新增 **`cap_embedding_texts()`** 兜底截断（**只截嵌入输入，payload 正文不受影响**）。

**Bug 2｜字符切片后 `row_start` / `row_end` 元数据错位。**
`splitter.py` 原先按 `slice_index * step` **估算**行区间；改字符切片后**步长不再是固定行数** ⇒ 元数据与内容错位
（被单测抓出 `Σ(row_end - row_start)` 出现负值）。
修法：表格循环改用 `slice_ranges()` 的**真实行区间**。抽 3 张表校验 `Σ(row_end - row_start) == table_row_count` 通过。

**修后预检（零 API 成本）**：12,301 块、p99 **1,196 字**、仅 1 块 13,239 字（走兜底截断）、行数守恒 OK；
重建日志中 `Range of input length` 错误 **0 次**。

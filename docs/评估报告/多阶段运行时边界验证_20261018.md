# 多阶段运行时边界验证（2026-10-18）

## 一句话结论

**三个边界中，BM25 常驻与词表自动加载已达标；冷态预热按“检索段”口径首查 780ms（<1s），但端到端含 embedding 为 1.17s，未达标。实体定向重试从 ~300ms 降到 5–13ms，B2007|2 检索段均值 388ms。v2 用当前检索重跑为 96.32%（133/138），B2007|2 为 17/17；此前 99.65% 未能复现，因此本轮不把主口径从 90.62% 替换为 99.65%，v2 继续作为内部候选。**

## 一、验收结果

| 边界 | 验收标准 | 实测 | 判定 |
|---|---|---|---|
| 冷态预热 | 启动预加载 BM25，首查 <1s | 检索段首查 **780ms**；端到端 **1,166ms**（embedding 约 380ms） | 检索段达标；端到端未达标 |
| BM25 可用性 | 常驻；不可用记 `bm25_unavailable_fallback`，不静默回退 | `bm25_status=ready`；异常路径单测覆盖并断言日志 token | 达标 |
| 词表自动加载 | 线上不依赖手动传 `known_entities` | `vocab_source=qdrant`，自动加载 **30** 个简称；Qdrant 失败降级 Excel，再失败为空并告警 | 达标 |

补充：多阶段运行时默认关闭（`MULTI_STAGE_RETRIEVAL_ENABLED=false`），因此不会给默认启动增加表级 BM25 的 23s 加载与 11s 预热。开启该开关后，API 启动阶段才执行预热。

## 三、代码改动

### 3.1 表级 BM25 常驻

- `src/core/table_bm25.py` 新增 `table_bm25_cache_target` 与 `build_table_bm25_cached`：
  - 缓存按“集合名 + 点数”命名，增量插入/重建自动换文件；
  - 缓存命中直接反序列化，未命中才滚动 `chunk_type=table` 建索引并落盘；
  - 首次构建约 26.7s，缓存加载约 2.7s。
- 新文件 `src/core/multi_stage_runtime.py`：
  - `build_multi_stage_runtime` 装配 Qdrant / Embedding / 表级 BM25 / 词表；
  - `load_known_entities`：Qdrant `distinct_stock_names()` → Excel → `none`；
  - BM25 构造失败设置 `bm25_status=unavailable`，记录 `bm25_unavailable_fallback collection=... error=...`，由 `MultiStageRetriever` 回退旧的扩召回逻辑；
  - `warmup()`：3 种查询形态 × `MULTI_STAGE_WARMUP_ROUNDS`（默认 3），向量只算一次并复用，避免预热消耗多次 embedding。
- `src/core/pipeline.py` 增加 `get_multi_stage_runtime()` 懒加载单例；`src/app/api.py` 在多阶段开启时启动预热，混合 BM25 预热失败也记录 `bm25_unavailable_fallback scope=hybrid_chunk_bm25`。
- 配置：`TABLE_BM25_INDEX_PATH`、`MULTI_STAGE_RETRIEVAL_ENABLED`、`MULTI_STAGE_WARMUP_ENABLED`、`MULTI_STAGE_WARMUP_ROUNDS`（`.env.example` 同步）。

### 3.2 实体定向重试降耗

上一版 `_bm25_entity_hits` 对 3,148 张表做全库 BM25 扫描（约 155–430ms）。本轮：

- `MultiStageRetriever` 启动时按 `stockName` / `stockCode` 建表级倒排（`_stock_doc_indices` / `_code_doc_indices`）；
- `BM25Retriever.retrieve(..., candidate_indices=...)` 只对覆盖点名主体的子集打分；`df` / `avgdl` 仍按全库统计，分值与全库扫描一致；
- 实体覆盖仍走 `hit_covers_entity` 的同一套 `resolve_names` / `name_matches` / `code_matches` 语义，不引入“猜实体”。

效果：`entity_retry` 从 ~300ms 降到 **5–13ms**；B2007|2 top-10 从“8 张点名主体 + 2 张其他公司”变为 **10/10 均为华润三九或白云山**，覆盖 2/2。

### 3.3 不精排时只取最终 top-k

不精排时，最终排序只依赖粗排分与行证据（均已在内存），无需先取回 `rerank_pool=50` 张整表：

- `_fetch_for_output` 先打分再取表，只 scroll 最终 top-k；
- `fetch` 从 ~120–1,692ms（50 张）降到 **30–47ms**（10 张）；
- 精排开启时仍取完整 `rerank_pool`，行为不变。

### 3.4 单测

- `tests/test_multi_stage_runtime.py`：词表 Qdrant/Excel 降级、BM25 fallback 日志、预热 9 次调用且 `top_k=10/row_k=200`、`context_queries` 透传；
- `tests/test_multi_stage.py`：BM25 子集打分与全库分值一致、空候选、实体倒排只返回点名主体；
- `tests/test_table_bm25.py`：缓存写入/复用、缓存命中不 scroll。
- 全量：**981 passed, 1 warning**。

### 4.3 与旧 99.65% 的差异

旧 `faithfulness_a_regenerated_v2_ascii_fix.json` 是 **124/124 = 100%**（12 题均值 1.0），但答案集与本次不同（本次 138 条 claim）。差异来源：

- **LLM 重生成波动**：B2007 旧 22 条 claim、本次 17 条；B2011 本次 23 条；B2010 本次 13 条。不是同一批答案，不能逐条对比。
- **评测器假阴性（3 类，已在本次 miss 中定位）**：
  - B2010|4：ASCII 坐标轴 `0 1000 2000 3000` 仍被当成数字 claim（解析成 `01000`、`3000`），遮罩未覆盖“带前导空格、无单位”的变体；
  - B2080|1：`561` 对证据表 `560.93`，四舍五入容差未命中；
  - B2002|1：`2.17`、`0.60` 实际在证据表 `中恒集团 2.17` / `华润三九 0.60` 行内，行级数字匹配未关联到该行。
- **可能真外推（2 个数字）**：B2010|4 的 `638`、`481` 百万元未在本次 top-10 证据表中找到；需要下一轮单独确认是“图表/正文证据未召回”还是“生成补数”。

因此：**99.65% 不是当前可复现的 v2 数值；当前可复现值为 96.32%。** 本轮不把主口径从 90.62% 替换为 99.65%。

### 4.4 决策

| 口径 | 数值 | 状态 |
|---|---:|---|
| 保守主口径（旧答案 + 同源证据，B2007 安全拒答记 0） | **90.62%** | **保持主口径** |
| v2（`--retrieval-query` + 实体定向重试，当前检索重跑） | **96.32%** | 内部候选 |
| 旧 v2（ASCII 修正后的旧答案集） | 100%（124/124） | 历史产物，不与本次混用 |

提升 v2 为默认的前置条件（下一轮）：

1. 修 3 类评测器假阴性（ASCII 轴变体、四舍五入、行内数字关联）；
2. 确认 B2010|4 的 `638`/`481` 是召回缺口还是生成补数；
3. 重跑 12 题，得到稳定 v2 后再决定是否替换 90.62%。

## 五、仍未做的边界（必须写清）

1. **线上链路未接多阶段检索。** `RAGPipeline.query()` / `agent_query()` 仍走手写/混合检索；`MultiStageRuntime` 目前只用于评测与 API 启动预热。即使 v2 数值达标，也还不是“线上默认”。
2. **默认开关关闭。** `MULTI_STAGE_RETRIEVAL_ENABLED=false`，避免无用的 23s 构建 + 11s 预热；开启后才有启动预热。
3. **Qdrant 延迟抖动。** 同机 10 次总延迟 P95 1,496ms；若要求端到端 P95 <1s，需要 Qdrant 侧调优（HNSW/资源隔离）或降低 coarse 深度并重新验证质量。
4. **B2079|1 top-10 与基线重叠 5/10。** 与改造前一致，是既有波动，不是本轮实体倒排引入；未在本轮处理。
5. **预热成本。** 3 轮 × 3 形态约 11.4s；若启动时间敏感，可把 `MULTI_STAGE_WARMUP_ROUNDS` 调到 1–2，但首查会回到 1.2–1.5s。

# 技术选型对比：表格检索链路的六个决策点

> 日期：2026-10-18
> 范围：研报表格检索、数据管道、两阶段召回与精排、行级事实、查询约束
> 证据口径：只写本仓库可复核的代码、报告或实测；没有同语料 A/B 的地方明确标为“未实测”，不引用无法核实的行业数字。

## 一、先看结论

| 决策点 | 本项目选择 | 核心理由 | 主要代价 / 边界 |
|:--|:--|:--|:--|
| 混合检索融合 | **RRF（排名融合）** | 不依赖向量分与 BM25 分的量纲，适合异构召回器 | 不能利用分数强弱；没有与加权求和的同语料 A/B |
| 召回与精排 | **Bi-Encoder 粗召回 + qwen3-rerank 精排** | 181K 级索引不可能对全库做 Cross-Encoder；精排只处理 20–50 条候选 | 精排模型内部结构未核实；无本地 Cross-Encoder 对照 |
| PDF 解析 | **MinerU + 自研 TableGrid 结构化** | MinerU 直接产出 Markdown/HTML 表格，能继续做表头、单位、坐标回表 | 没有 MinerU vs LayoutLM 的同语料 A/B |
| 检索单元 | **整表块为主，row_fact 隔离使用** | 169,234 条行事实与 5,739 个表块约 29.5:1，混入普通召回会稀释表块 | 行级事实仍缺少表级 gold；`row_hits` 只证明约束成立，不证明足以回答 |
| 检索阶段 | **单阶段为线上基线，多阶段保留实验** | 表级粗召回能减少 row_fact 稀释，但行级精定位在当前语料上覆盖有限 | v5 的 22/27 是假阳性；v6 只有 4/27 约束成立 |
| 查询约束 | **软匹配用于排序，硬匹配只在约束确定时启用** | 软过滤不能真正移除候选；硬过滤能改变 top-10 | 硬匹配必须有“抽不到约束就不过滤”的退路，否则会制造空上下文 |

一句话：**当前链路的核心不是“把所有新组件都接上”，而是把“召回什么、返回什么、证据能证明什么”三层分开。**

## 二、统一评价标准

本文用同一组标准比较方案，而不是只比较单点命中率：

| 维度 | 要回答的问题 | 本项目关注点 |
|:--|:--|:--|
| 相关性 | top-10 是否包含能回答问题的内容 | 同主体、真内容、表级/行级命中 |
| 可追溯性 | 答案里的数字能否回到原表单元格 | `anchor_cells`、`table_id`、行列坐标 |
| 可审计性 | 引用是否来自用户能看到的材料 | 引用与证据材料同口径 |
| 延迟 | P95 是否可接受 | 不能把冷/热缓存混合值当稳定结论 |
| 成本 | 是否需要全库重编码或逐条 LLM 调用 | 表格结构化、精排候选数、embedding 费用 |
| 可维护性 | 新增字段能否进入契约并单测 | 默认开关、版本化、回滚边界 |

## 三、RRF vs 加权求和

### 3.1 问题

向量检索返回余弦相似度，BM25 返回词频/逆文档频率得分，两者量纲不同。直接做加权求和，必须先做归一化；归一化方式会改变最终排序，且不同查询的分数分布并不稳定。

### 3.2 候选

- **加权求和**：`score = α·norm(vector) + (1−α)·norm(bm25)`，可解释、可调权重，但需要额外校准。
- **RRF**：`score(d) = Σ 1/(k + rank(d))`，只使用排名，不比较原始分数。项目取 `k=60`。

### 3.3 项目实现

| 项 | 事实 |
|:--|:--|
| 开关 | `HYBRID_ENABLED=true`，混合检索为当前默认 |
| 向量路 | `HYBRID_TOPK_VECTOR=200` |
| BM25 路 | `HYBRID_TOPK_BM25=200`，`K1=1.5`、`B=0.75` |
| 融合 | `src/core/retrievers.py` 的 RRF，`score += 1/(rrf_k+rank+1)` |
| 保底 | `HYBRID_VECTOR_FLOOR_RATIO=0.95`，避免 BM25 关键词路挤掉向量路高质量文档 |

### 3.4 实测证据

来自 `docs/评估报告/检索对比实验.md`，口径为 84 个检索测试、61 个有引用题：

| 配置 | 文件级命中（纯向量→混合） | 数字级命中（纯向量→混合） |
|:--|--:|--:|
| K=50 + Rerank，召回层 | 48.5%→48.8% | 70.2%→**74.9%（+4.6pp）** |
| K=100 + Rerank，召回层 | 56.5%→57.7% | 75.1%→**79.4%** |
| K=50 + Rerank，精排后 top-10 | 21.0%→21.6% | 57.4%→58.3% |
| K=50 + Rerank，精排后 cap=2 | 未单列 | 混合口径 **59.1%** |

结论：

1. 混合检索在数字级命中上稳定优于纯向量，召回层提升约 1.8–4.6pp。
2. 精排后增益收窄，说明**召回层是上限，精排不能把没召回的文档变出来**。
3. K 从 50 加到 100 能提高召回层覆盖，但精排后 top-10 反而下降；因此项目保留 K=50，而不是盲目加深。

### 3.5 决策与边界

**选择 RRF。** 主要理由是工程稳健性：不需要为每次查询重新校准两路分数的分布，且 BM25 与向量路的召回深度可以独立配置。`vector_floor_ratio=0.95` 是针对“BM25 关键词路可能挤掉向量路”的保底，不是对 RRF 公式的修改。

**没有做的事：**

- 没有在同一语料上跑“RRF vs 加权求和”的 A/B；不能声称 RRF 一定优于加权求和。
- 没有对 BM25 分词做领域词典/中文分词器对比；当前是英文/数字词 + 中文单字。
- 181K 点的 row_fact 全索引尚未跑通 BM25（内存限制），因此混合检索的 181K 结论只适用于表/正文过滤后的候选层，不适用于全库 row_fact。

## 四、Cross-Encoder vs Bi-Encoder

### 4.1 问题

需要在“召回覆盖”和“精排精度/延迟”之间做取舍。对 181K 级索引逐条做 query-document 联合编码不现实。

### 4.2 项目实现

项目实际是两阶段：

1. **粗召回**：`text-embedding-v2`，1536 维，Bi-Encoder 式向量化，Qdrant 近似检索。
2. **精排**：`qwen3-rerank`，项目按 Cross-Encoder 式 API 使用；只对候选集做联合打分。

| 参数 | 值 |
|:--|:--|
| `RETRIEVAL_K` | 50 |
| `RERANK_TOP_N` | 10 |
| `RERANK_OVERSAMPLE` | 2 |
| `RERANK_MAX_PER_FILE` | 2 |

### 4.3 实测证据

- 召回层数字级命中：K=50 混合 **74.9%**；K=100 混合 **79.4%**。
- 精排后 top-10 数字级命中：K=50 混合 **58.3%**；每文件 cap=2 时 **59.1%**。
- K 加深后召回层提高，但精排后 top-10 没有同步提高，说明精排和“每文件上限”会重新分配名额，不能把召回层指标直接当最终质量。

### 4.4 决策与边界

**选择两阶段。** Bi-Encoder 负责“从大池子里找得到”，Cross-Encoder 式精排负责“在少量候选里排得准”。这是一条成本可控的工程折中。

**未实测：**

- 没有本地 Cross-Encoder（如 bge-reranker）与 `qwen3-rerank` 的同语料 A/B。
- 没有 `qwen3-rerank` 的独立 P50/P95 延迟报告；现有端到端 P95 含检索、精排、生成等多段，不能拆成精排延迟。
- 没有验证精排模型内部结构，因此文中只说“Cross-Encoder 式 API”，不把它写成已核实的模型架构。

### 4.5 消融补充：精排在表格检索场景可能有害（2026-10-18）

A 类 12 题 claim-level faithfulness 消融：

| 配置 | 题均支持率 |
|:--|--:|
| 向量 + 行证据排序（无精排） | 46.26% |
| 只开 qwen3-rerank | **37.68%** |
| 门控 BM25 + 无精排 | **47.06%** |

只开精排相对无精排回退 8.58pp。逐题看，精排把“含答案数字的具体表”换成了“主题更相关的行业综述表”（B2002|1 90.0%→50.0%，B2077|1 78.9%→31.6%）。把命中行证据置顶后仍为 37.22%，排除“4000 字截断”解释。

原因是精排优化的是 query-document 语义相关性，而表格检索需要的是**证据充分性**（这条 claim 的数字/期间是否真的在表里）。这与 TableSeek 提出的“语义相关≠证据充分”洞察一致，本仓库给出同语料实证。

**决策**：精排不设为表格检索默认；保留为可选重排，或在“语义相关但证据不足”的场景做证据感知重排（按 claim 数字/期间命中率二次排序）。

## 五、MinerU vs LayoutLM / LayoutLMv3

### 5.1 问题

研报 PDF 的表格需要变成可检索、可回表的结构。两条路线：

- **MinerU**：通用 PDF 解析，直接输出 Markdown/HTML，后续可继续做表格对象化。
- **LayoutLM / LayoutLMv3**：利用版面坐标与视觉特征做版面分类、实体抽取或表格理解，通常需要标注与训练。

### 5.2 项目实现与实测

| 项 | 事实 |
|:--|:--|
| 研报语料 | 473 篇（个股 160 + 行业 313） |
| 原始表数 | 3,343 张 |
| `<th>` 表头 | **0 张**；表头同样是 `<td>`，不能靠标签判定 |
| 自研结构 | `TableGrid` / `Table`，推断表头、键值卡片、跨列标题、合并单元格 |
| 人工核对 | 20 张表工作单；10 张 Gold Set + TEDS 简化版 |
| 全库机器核对 | 3,343/3,343 行数守恒与列数比对通过（0 差异） |

结构化前后（473 篇离线对比）：

| 项 | legacy | structured | 变化 |
|:--|--:|--:|--:|
| chunk 总数 | 57,031 | **10,687** | **−81.3%** |
| 表格 chunk | 49,913 | 3,711 | −92.6% |
| 平均块长 | 182.9 字 | **1,012.3 字** | +453% |
| 总字符量 | 10.43M | 10.82M | **+3.7%** |

注意：**点数下降不等于嵌入 token 下降**。Markdown 表头、分隔符和 caption 会让总字符量略增；收益主要在“表格不再被拆成一行一个 chunk”和“行列语义可回表”。

### 5.3 决策与边界

**选择 MinerU + 自研 TableGrid。** 原因是本项目要解决的是“把表格还原成可检索的单元格结构”，而不是只做版面分类。MinerU 的输出能直接进入后续的表头推断、单位回退、`anchor_cells` 和标注迁移链路。

**未实测：**

- 没有 MinerU 与 LayoutLM/LayoutLMv3 在同一批 473 篇研报上的 A/B。
- 没有 LayoutLM 的训练成本、标注成本、推理延迟数据。
- 不能声称“MinerU 一定优于 LayoutLM”；更准确的说法是：在当前“无需训练、要保留表格结构”的约束下，MinerU 是更直接的工程选择。

## 六、整表向量 vs 行级事实

### 6.1 问题

整表向量把一张表作为一个检索单元，容易“表对了但行不对”；行级事实把每个“指标 × 期间 × 数值”变成可检索单元，但会产生大量细粒度候选，稀释整表召回。

### 6.2 实测证据

v5 集合把 169,242 条 row_fact 混入普通召回后：

| 配置 | HR@10 | nDCG@10 |
|:--|--:|--:|
| 全索引（含 row_fact） | 0.0267 | 0.0512 |
| 排除 row_fact 后 | **0.0656** | **0.1002** |

排除 row_fact 后指标精确恢复到原基线，说明**不是 row_fact 的内容错了，而是它不该和表块/正文块在同一个 top-K 池里竞争**。

v6 集合的分层：

| chunk_type | 点数 |
|:--|--:|
| row_fact | 169,234 |
| table | 5,739 |
| prose | 6,443 |
| boilerplate | 119 |
| **合计** | **181,535** |

row_fact : table ≈ **29.5 : 1**。如果直接混合召回，平均每召回 30 条才可能有 1 条表块，整表证据会被系统性稀释。

### 6.3 决策与边界

**整表块作为返回单元，row_fact 只作为隔离的候选/证据层。** 多阶段路径是“表级粗召回 → 行级精定位 → 整表返回”，而不是“把 row_fact 混进普通 top-50”。

边界必须写清：

- `row_hits` 只证明指标/期间约束成立，不证明该行足以回答问题。
- v6 只有 4/27 题有约束成立的行证据；这不是“行级事实已经可用”，而是“硬匹配后剩下的真实覆盖”。
- 行级事实需要有表级 gold 才能算正确率；当前没有。

## 七、单阶段 vs 多阶段

### 7.1 设计

多阶段检索的三步：

1. 只在 `chunk_type=table` 中做表级粗召回；
2. 只在候选 `table_id` 内查 row_fact，做行级精定位；
3. 按 `table_id` 拉回整表切片，按 `table_slice_index` 拼接后返回。

### 7.2 实测

27 条点名公司题：

| 模式 | 集合 | 同主体 | 真内容 | 有行证据题数 | 空上下文 | trace P95 |
|:--|:--|--:|--:|--:|--:|--:|
| single | v5 | 2.15 | 1.74 | 0/27 | 8 | 2933.7ms |
| table_first | v5 | **2.78** | **2.33** | **22/27（假阳性）** | **5** | 1760ms |
| single | v6 | 2.19 | 1.78 | 0/27 | 11 | 1807.2ms |
| table_first | v6 | 2.44 | 2.00 | **4/27（约束成立）** | 10 | 556.6ms |

解读：

1. 表级粗召回确实改善了同主体与真内容，但 v5 的 22/27 行证据大量不满足指标/期间，是错误行分把表排上来的假阳性。
2. v6 加了单位回退和指标/期间硬匹配后，真内容从 2.33 降到 2.00；这不是退化，而是**挤掉假阳性的代价**。
3. v6 的 4/27 才是“约束成立”的行证据；不能把它写成“行级证据正确率 4/27”，因为分母不是人工表级 gold。
4. 556.6ms 与 1807.2ms 是冷/热缓存混合的 trace P95，不能作为稳定延迟结论。

### 7.3 决策

**多阶段保留为实验路径，不切线上默认。** 当前收益主要来自“表级粗召回”，而“行级精定位”的覆盖受语料限制。下一步应先建立表级 gold，再决定是否把多阶段变成默认链路。

## 八、软匹配 vs 硬匹配

### 8.1 问题

查询里解析出公司、期间、指标后，是“给候选加权”还是“直接删掉不匹配候选”？

### 8.2 项目事实

- 实体闸门 `ENTITY_GATE_ENABLED=false` 默认关闭，`ENTITY_GATE_MIN_KEEP=0`，`ENTITY_GATE_KEEP_UNKNOWN=true` 必须保留。
- 配置注释明确指出：软约束只是改变候选排列；精排吃完整候选池且对输入顺序不敏感，**只有硬过滤能真正移除候选、改变 top-10**。
- 27 题实测：`min_keep=3` 有 11/27 题跳过过滤，其他公司占比 0.1333；`min_keep=0` 时其他公司占比 0，且本主体命中率相同。`min_keep=3` 不划算。
- 行级硬匹配 `src/filters/row_match.py`：期间精确匹配，`2025Q3` 不匹配 `2025A/2025E`；指标别名归一；空约束不过滤；有期间但行事实缺期间时判不匹配。

### 8.3 决策与边界

**两层策略：**

- 软匹配用于排序和召回扩展，保留上下文安全；
- 硬匹配只在“问题明确给出主体/期间/指标”时启用，且必须有“约束抽不到就不过滤”的退路。

边界：

- `ENTITY_GATE_KEEP_UNKNOWN=true` 不能关；语料里有 7 条点名公司题的公司不在研报库内，关掉会清空上下文。
- 硬匹配不是越多越好。B2065/B2069/B2015 的 0 行证据，首先是因为研报表没有季度实际值，而不是过滤代码误杀。
- 硬匹配的收益必须和空上下文率一起看；只看命中率会鼓励过度过滤。

## 九、跨方案风险与失效边界

### 9.1 HNSW 索引事故

v6 重建后出现过一次 Qdrant 临时段 rename `Permission denied`，重启后 HNSW 近似检索异常：同内容、同向量、同 query 的 exact 得分为 0.654，但默认 HNSW 连 top-1000 都进不去。强制重建 HNSW（m=17、segments 4→2）后恢复为 **181,535/181,535 全部索引、green**。

**规则：HNSW 修复前的评测结果作废。** 任何索引重建后，先做“同向量 exact vs HNSW”自检，再跑评测。

### 9.2 指标口径风险

| 风险 | 表现 | 处置 |
|:--|:--|:--|
| 把约束成立当答案正确 | `row_hits>0` 就宣称行级证据可用 | 只写“约束成立”，不写“正确回答” |
| 把 v5 的 22/27 当基线 | 用假阳性行分解释精度 | 明确 v5 为修复前基线，v6 的 4/27 才是硬匹配后覆盖 |
| 把 trace P95 当稳定延迟 | 冷/热缓存混在一起 | 标注“非稳定口径”，需要单独压测 |
| 把结构化点数下降当 token 下降 | 以为重建一定更便宜 | 点数 −81.3%，字符量 +3.7%，成本要分开算 |

### 9.3 未实测清单

- RRF vs 加权求和的同语料 A/B。
- 本地 Cross-Encoder 与 `qwen3-rerank` 的精度/延迟对照。
- MinerU vs LayoutLM/LayoutLMv3 的同语料 A/B。
- 181K 点 row_fact 全索引的 BM25 构建与检索。
- 多阶段检索的稳定 P99 与并发压测。
- 表级 gold（当前只有 10 张表 Gold Set + TEDS 简化版，不是 27 题表级标注）。

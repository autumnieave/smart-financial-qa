## 1. 项目背景与业务目标

### 1.1 背景与痛点
- 投研/财务分析场景中，分析师从财报 PDF 人工拆解财务数据效率低、易漏易错；
- 通用大模型直接回答财务数值存在幻觉风险（数字编造、口径混淆）；
- 研报观点类知识以长文本非结构化形式存在，检索与引用溯源困难。

### 1.2 系统定位
- 面向上市公司财务问答的端到端系统：用户用自然语言可查财务数据（结构化）与研报观点（非结构化），答案带来源可追溯。
- 数据面：473 篇券商研报（观点）+ 1252 份深/上交所财报 PDF（字段）双语料入库。

### 1.3 业务目标与非目标
| 类型 | 内容 |
| --- | --- |
| 目标 1 | 自然语言 → 可靠 SQL：语句级编译通过率 100%（可复现口径） |
| 目标 2 | 观点问答带引用：引用文件 100% 可溯源、答案数字可溯源、真实幻觉 0 例 |
| 目标 3 | 全链路工程化：244 个离线单测 + CI；容器化一键部署 |
| 目标 4 | 可评测：golden 版本化，任何改动可回答「改了什么、怎么证明变好」 |
| 非目标 | 不面向真实线上用户提供生产收益指标；不承诺语义全量自动判定（语义层靠抽样人工） |

### 2.2 决策路径划分（M/R 分界的设计理由）
| 路径 | 特点 | 系统内环节示例 | 治理手段 |
| --- | --- | --- | --- |
| 模型决策路径（M） | 输出不确定、成本高、会漂移 | 任务拆解、指标标准化、SQL 生成、分析文本、图表 JSON、RAG 答案生成、聚合汇总 | 全部配规则闸门/重试/自洽性核验；Prompt 版本化 + 三层结构治理 |
| 确定性规则路径（R） | 输出可断言、可单测、零外部依赖 | 静态校验、MySQL 编译试运行、RRF 融合、软过滤、表聚合、引用构建、L1 核验、缓存、checkpoint/记忆、请求路由 | 单测覆盖（tests/）、CI 自动执行 |

- 设计理由：两类错误来源不同——M 类错误（幻觉/口径漂移）用「约束+校验+回归」控制，R 类错误（索引错位/解析失败）用「单测+守卫」控制。所有 M 环节的产出必须经过至少一个 R 环节才能进入下一步。

### 2.3 三类问题的数据流（同一条架构下三种编排）
| 问题类型 | 主路径 | 说明 |
| --- | --- | --- |
| 纯财务数值类 | supervisor → 财务 worker（SQL 链路）→ 直出 | 单任务直出跳过聚合，省 1 次 LLM 调用（AGENT_MULTI_DIRECT_RESULT=true） |
| 纯研报观点类 | supervisor → 研报 worker（RAG 链路）→ 直出 | 开放性/观点题可能判定空 SQL，直接研报作答 |
| 混合类（数据+观点） | supervisor → 两 worker 并行 → aggregator 聚合 → finalize | ThreadPoolExecutor 并行取数，聚合层输出带引用答案 |

### 2.4 关键架构约束（来自 AGENTS.md 与代码）
- 新链路必须实现 core/interfaces.py 的 IRetriever/IReranker/IGenerator，禁止绕过接口直连具体类；
- 会话状态统一走 RAGPipeline._load_conversation/_save_conversation（按 user_id，支持序列化）；
- 新增 Prompt 只允许放 prompts/ 并 bump PROMPT_VERSION；
- 回归/核验统一走 python -m eval，禁止散装评估脚本。

### 2.5 量化证据与本章小结
- 【指标】SQL 137/137=100%、引用 1080/1080、数字可溯源 4068/4071（99.9%）、单测 244——分别对应 L2 编排、L3 RAG、L6 评估、L0-L6 工程质量四个层。

## 3. 核心模块详细设计

### 3.1 Agent 调度层（LangGraph StateGraph · Supervisor-Workers）

#### 3.1.1 状态机与节点（agents/langgraph_multi_agent.py:114-132）
```text
START → supervisor ──条件边──► tools（_run_subtasks，并行）──► direct ──► END
        （拆解 M）              （ThreadPoolExecutor）      （单任务直出 R）
                                  │ 多任务
                                  ▼
                             aggregator（聚合 M）──► finalize（R）──► END
```
- 条件边路由：supervisor 输出结构化任务列表；1 个任务走 direct，多个任务走 aggregator，非法 JSON 回退主模型重试（logger.warning 记录，:144）。
- 子 Agent：财务 SQL worker（call_financial_chatflow）与研报 RAG worker（research 子任务）并行取数。
- Checkpoint：默认 sqlite 落盘（database/langgraph_checkpoints.sqlite），降级 memory；thread_id 绑定 user_id；状态含 last_active 新鲜度，超时按新话题处理（:426-427）。
- 会话记忆双层：LangGraph checkpoint（图执行状态）+ memory/store.py ConversationState（业务状态，SQLite/Redis 双后端，TTL 默认 86400s，to_dict/from_dict）。

#### 3.1.2 关键决策表
| 决策点 | 当前实现方式 | 设计推荐标准 | 差异点（客观） |
| --- | --- | --- | --- |
| supervisor 模型 | 默认 SUPERVISOR_MODEL=qwen-flash（快模型），非法 JSON 回退主模型 | 预留「规划预算」：拆解结果 schema 校验 + 最大重试次数外置可配 | 当前回退策略在代码内固化；推荐将重试/预算收敛到配置与契约层 |
| 并行实现 | ThreadPoolExecutor 线程级并行子任务 | 演进可评估 langgraph Send API 并行（仓库内已列为待办） | 两者结果等价性需同口径回归验证后再切换 |
| 单任务直出 | AGENT_MULTI_DIRECT_RESULT=true，跳过聚合省 1 次 LLM | 直出判定增加「是否需要观点补充」的显式信号 | 当前以任务数量为唯一判据 |
| 会话持久化 | checkpoint(sqlite/memory) + ConversationState(SQLite/Redis) 双层 | 增加会话生命周期管理（归档/清理策略）与跨栈一致性校验 | 双层写路径需保证原子性（当前为顺序写） |
| 可观测 | logger 事件 + stage 回调（on_stage） | 节点级 span（见第 8 章「可观测性」差距自评） | 当前无分布式 trace |

#### 3.1.3 量化证据
- 【指标】LangGraph 对照版同口径回归 91.3% → 108/108=100% 后转主链路（docs/评估报告/LangGraph对照.md）；多 Agent 财务向子集 8 题 7/7（只换编排层）。
- 【指标】性能：财务/研报并行 + 单任务直出 + 关 thinking 后，10 题总耗时下降约 39%（docs/评估报告/性能优化_并行缓存.md）。

### 3.2 Text-to-SQL 链路（Schema+白名单 → 生成 → 静态校验 → MySQL 试运行 → 执行 → 分析+图表）

#### 3.2.1 流程与防线
```text
用户问题
  │ ① 指标标准化（可选，AGENT_METRIC_STANDARDIZE）：抽指标口径 JSON（M）
  │ ② Schema + 字段白名单约束生成 SQL（M，prompts/financial.py：11 条规则 + 约 60+ 白名单字段）
  ▼
③ 静态校验 validate_sql（R，tools/sql_validator.py）：仅 SELECT / 字段-表归属 / 别名 / 全角标点
  │ 失败 → 错误回灌 LLM 重写（AGENT_NATIVE_RETRY=2）
  ▼
④ MySQL 编译试运行 compile_check（R，tools/sql_validator.py:317，max_execution_time=15000ms）
  │ 超时/失败 → 带错重试
  ▼
⑤ 执行查询（connect_timeout=5s，tools/native_financial.py:699）→ DataFrame
  │
  ▼
⑥ 自动分析（M）+ 自洽性核验（R，失败重试 1 次）→ ECharts 图表 JSON（解析失败仅软降级跳过）
```

#### 3.2.2 白名单与安全规则（当前实现方式）
| 项 | 内容 | 实现位置 |
| --- | --- | --- |
| 表白名单 | 仅 core_performance_indicators_sheet / balance_sheet / cash_flow_sheet / income_sheet | tools/sql_validator.py WHITELIST_TABLES |
| 字段归属 | SELECT/FROM/JOIN 字段必须存在于对应表，含别名解析与同名歧义拦截 | tools/sql_validator.py（sqlparse） |
| 语句类型 | 仅只读 SELECT，拦截 DDL/DML/事务及混入文本 | tools/sql_guard.py |
| yoy 字段 | 同比/环比仅限库内现成字段，禁止编造 *_yoy/_growth | tools/sql_guard.py:61-80 动态注入 |
| 超时熔断 | 编译试运行 15000ms；连接 5s；LLM 300s | tools/sql_validator.py:317、config/rag_config.py |

#### 3.2.3 当前实现 vs 设计推荐（客观差异）
| 设计点 | 当前实现方式 | 设计推荐标准 | 差异点（客观） |
| --- | --- | --- | --- |
| 危险 SQL 特征库 | 以 sql_guard/sql_validator 规则函数形式存在（拦截白名单表外/非 SELECT/字段归属） | 独立 tools/sql_signatures.py 特征表 + 单测（SLEEP/BENCHMARK、注释剥离、系统库探测等） | 现有能力=函数内聚规则，推荐=独立可审计特征库 |
| 重试策略 | 固定重试 2 次，错误文本回灌 | 按错误类型分级（compile/validate/timeout）设定重试与降级 | 现为统一计数 |
| 分析自洽性 | 自洽性核验 + 重试 1 次（tools/native_financial.py:483） | 核验规则外置为守卫清单（financial_mean_guard 已有先例） | mean_guard 已单测固化，其余规则仍内联 |
| 结果可复现 | 缓存 key 含 FINANCIAL_PROMPT_VERSION/QUERY_CACHE_VERSION，真实回归关缓存 | 生成物（SQL/分析/图表）落盘 jsonl 留档 | 部分回归脚本已落 jsonl（golden_answer_regression） |
| 空 SQL 语义 | Agent 判定无需查库时返回空 SQL（B2002/B2004/B2077），计决策非失败 | 空 SQL 需携带 reason 字段回写结构化 | 当前仅能从日志/结果推断原因 |

#### 3.2.4 量化证据
- 【指标】80 题全量回归：96.9%（基线 282/291）→ 100%（224/224 Dify 历史；102/102、137/137@09-05 原生链路）；9 条 badcase 修复闭环；两步分解冒烟 24/24（2026-09-06）。
- 【指标】80 题回归中图表 JSON 软降级 6 次（文本答案与 SQL 不受影响），已登记为待归集项（docs/评估报告/端到端复验快照_2026-09.md）。

### 3.3 RAG 检索与引用核验链路

#### 3.3.1 链路图
```text
MinerU 解析 473 篇研报（OCR/表格/公式，离线）
  ▼
层级分块 + 表格聚合（overlap=100，5 档对比实验确定；表格行命中回拉父表）
  ▼
Embedding：text-embedding-v2，1536 维（分批 10 + 指数退避重试）
  ▼
Qdrant research_reports_v3_full（payload 软过滤元数据）
  ▼
混合检索（R）：向量路 top200 + BM25 路 top200 → RRF(k=60) 融合 → 向量保底 0.95
  ▼
软过滤打分（filters/query_filters.py）→ 表聚合（TABLE_AGG_TOPK=20）
  ▼
qwen3-rerank 精排：K=50 → top10（oversample×2，每文件 ≤2）
  ▼
引用构建 + L1 过滤（pipelines/rag_pipeline.py validate_citations：缺文件引用按配置过滤）
  ▼
LLM 生成带引用答案（llm/generator.py + prompts/rag.py，SSE 流式）
```

#### 3.3.2 关键设计点（当前实现方式）
| 设计点 | 说明 | 证据 |

### 4.1 接口总览

| POST | /chat/clarify | 多轮澄清对话（自动澄清通道） | JSON | app/api.py:229 |

### 4.2 REST 请求/响应模型（app/schemas.py）

#### 4.2.1 ChatRequest（POST /chat、/chat/stream）
| 字段 | 类型 | 必填 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| question | string | 是 | - | 用户问题 |
| user_id | string | 否 | default | 会话标识（checkpoint/记忆/缓存按此隔离） |
| mode | string | 否 | rag | rag 或 agent（编排模式选择） |

#### 4.2.2 ChatResponse（POST /chat 返回体）
| 字段 | 类型 | 说明 |
| --- | --- | --- |
| content | string | 答案正文 |
| image | string[] | 结果图片（默认空数组） |
| references | object[] | 引用列表，元素含 paper_path / text 等 |
| chart_json | object? | ECharts 图表配置（可空） |

#### 4.2.3 ClarifyRequest / 响应（POST /chat/clarify）
- 请求：input(string)、user_id(string, 默认 default)。
- 响应：content / image / references / clarify_done(bool，是否已补齐条件完成检索)。

#### 4.2.4 错误语义
- 服务内部异常：HTTP 500 + detail（/chat/clarify 经 HTTPException）。
- 业务兜底：Agent 财务查询在 MySQL 不可用时返回友好错误 JSON；图表解析失败仅跳过图表不影响文本（软降级）。

### 4.3 SSE 事件定义（POST /chat/stream，media_type=text/event-stream）
- 传输格式：data: {json}\n\n（标准 SSE）。

| type | 载荷字段 | 语义 | 出现时机 |
| --- | --- | --- | --- |
| stage | stage: string | 阶段事件（agent 模式即时反馈，如任务拆解/取数中） | agent 编排过程中 |
| content | text: string（4 字符小块） | 生成内容增量（打字机效果） | rag 真实逐 token / agent 完成后重放 |
| meta | image / references / chart_json | 最终结果元数据（引用/图表/图片） | 内容结束后、done 前 |
| final | - | 通知前端重置（流式草稿与终稿不一致，如混合题：研报草稿→汇总终稿） | content 之后重发终稿前 |
| done | - | 本次问答结束 | 末尾 |
| error | message: string | 异常终止 | 任意时刻 |

#### 4.3.1 事件序列示例（agent 混合题）
```text
data: {"type":"stage","stage":"planning"}
data: {"type":"stage","stage":"fetching"}
data: {"type":"content","text":"正在汇总..."}
data: {"type":"final"}
data: {"type":"content","text":"答案内容(逐块)"}
data: {"type":"meta","references":[{...}],"chart_json":{...}}
data: {"type":"done"}
```

#### 4.3.2 缓存命中回放（当前实现方式）
- /chat 与 /chat/stream 均先查 SQLite 查询缓存（key=make_cache_key(chat, mode, user_id, question)）；命中则回放 meta + content + done，跳过真实检索与生成（app/api.py）。
- 真实重跑（评测）必须 QUERY_CACHE_ENABLED=false 或清缓存（utils/query_cache.py clear()）。

### 4.4 设计推荐标准（接口层，客观差异）
| 设计点 | 当前实现方式 | 设计推荐标准 |
| --- | --- | --- |
| 鉴权 | 未内置鉴权（内部/演示使用） | 接入 API Key/JWT 与频控（企业接入真实用户前） |
| 版本化 | /chat 无版本前缀 | /v1/chat 路径版本化 |
| 错误模型 | 混合（HTTPException + 业务 JSON） | 统一 error code + trace_id 回传 |
| 流式超时 | 依赖任务执行 | 增加服务端 keepalive 与客户端重连/续传协议 |
| 输入校验 | 长度无硬上限 | question 长度/频率/敏感词前置校验 |

### 4.5 接口契约出处
- app/schemas.py（请求/响应模型）、app/api.py（路由与 SSE 实现）、qa-frontend/src/（fetch 流式消费与渲染）。

### 6.5 用例库管理与 golden 回归闭环（准入 → 门禁 → 人工回查 SOP）

#### 6.5.1 golden 版本管理机制（当前实现方式）
- database/golden/manifest.json 版本注册（v1：2026-08-22，SQL 基线 80 题 / 108 子问题 / 291 句；v2：2026-09-09，对抗挑战集 18 条 / 5 类，kind=challenge），快照 JSON 不可变 + 源文件 sha256 防篡改（eval/golden.py init/verify）；
- golden 只进新版本、不原地改题：v1 不变，后续缺陷题以「新增版本 + 回归集」方式沉淀，修复后纳入回归集属正常防回退闭环；
- 真实重跑纪律：QUERY_CACHE_ENABLED=false 或清缓存；提示词改动 bump PROMPT_VERSION / QUERY_CACHE_VERSION（防「改了提示词命中旧缓存」）。

#### 6.5.2 新增测试用例准入流程（badcase → 单测 → golden，SOP 设计）
```text
线上/人工发现问题
  → 登记 badcase_台账.md（现象 / 复现问题 / 根因分类）
  → 根因判定：
      规则层缺陷 → 先写复现单测（tests/，零外部依赖）→ 修复守卫/校验器 → 单测转绿
      提示词/链路缺陷 → bump 版本 → 跑 golden 子集回归 → 通过率不回退
  → 纳入 golden 新版本（v2…）防回退（评审通过后固化）
```
- 已落地证据：9 条编译类 badcase 全修复并纳入回归；B-07~B-12 语义缺陷转守卫单测（tests/test_financial_mean_guard.py）。
- 准入 checklist：【已落地 2026-09-09，B-22 阶段 A】每条挑战条目必带「复现路径 / 期望行为 / 通过标准 / 类别 / 台账编号」（eval/golden.CHALLENGE_REQUIRED_FIELDS 强校验 + 编号唯一 + 类别白名单），评审通过才固化进 golden（阶段 B 已执行 + 人工抽审 18/18 回填 2026-09-10，行为缺陷转 B-26~B-29；B-26~B-29 已于 2026-09-10 修复复跑，新缺陷转 B-30/B-31，其中 B-31（库外指标统一出口 refuse.metric_out_of_scope）已于 2026-09-10 闭环并复跑，见 §6.7.4）。

#### 6.5.3 PR 合并前质量门禁（CI 扩展计划，设计推荐）
- 现状：CI 仅 pytest tests/（.github/workflows/ci.yml，push/PR 触发）。
- 计划（分层递进）：
  - 第 1 层（必过）：pytest 全量 + 覆盖率门禁（核心模块 ≥80%，先跑基线再设阈值）+ lint（ruff）；

  - 门禁产物：一次 PR 一份质量报告（单测 / 覆盖率 / 子集回归），留档可查。

#### 6.5.4 人工回查幻觉 SOP（当前实践 + 规范化模板）

- 规范化 SOP（设计推荐）：
  - 抽样比例：发布 / 大改动 100% 回查；日常迭代 ≥20%（每轮随机抽 ≥10 题）；
  - 周期：版本发布前必查 + 每周 1 次抽样；
  - 记录模板（每次一份）：日期 / 版本 / 样本范围 / 回查人数 / 核对项（数值口径、引用定位、是否基于引用作答）/ 幻觉例与根因 / 结论；

### 6.7 AI 应用特有测试（非确定性 / 检索质量 / 幻觉 / 对抗）

> LLM 应用与确定性软件差异显著：同输入可能不同输出、检索相关性 ≠ 事实正确、幻觉与提示注入是新增风险面。本节为「设计推荐」分阶段计划；当前已交付证据为人工回查与代理指标，标注现状与计划。

#### 6.7.1 非确定性测试（同题一致性）
- 目标：回答在「结构、数值、引用」三层面稳定可复现。
- 设计：结构一致性（同题 n=5 输出 JSON Schema 通过率 100%，复用 3.5.5 schema）；数值一致性（重复回答中关键数值集合交并比 ≥ 阈值）；引用一致性（重复回答引用文件/片段重叠率 Jaccard 作漂移信号）；语义一致性（LLM-as-judge，与 6.7.3 共用）。
- 已落地（B-17，2026-09-09）：结构维度由 utils/output_contracts.py 契约模块承载（supervisor / aggregator / metric / SQL 四类），格式错误事件落盘 训练结果数据/output_contract_stats.jsonl；真实指标标准化 10 题冒烟格式错误率 0/10（docs/评估报告/输出契约层B-17.md）；supervisor / aggregator / SQL 事件随真实 Agent 调用自动累计。
- 计划：eval 新增 consistency 套件（golden 子集 10-20 题 × n=5）；当前无数据 → 待补。

#### 6.7.2 RAG 检索质量评估（Recall@K / MRR / Precision@K）
- 现状：以「文件级可溯源 + 数字命中率」为代理指标（召回层 74.9%，K=50），不直接度量检索排序质量。
- 设计：构建 retrieval golden 子集（从 108 子问题选 30-50 题，人工标注每题关联片段，top-K=10）；指标：Recall@K（K=10/20）、Precision@K、MRR（首个相关片段位置），叠加现有数字命中 / 文件溯源作为业务向指标。
- 应用：检索参数（top-K / RRF k / rerank 数）调参与混合检索开关的量化依据，替代「只看生成答案」的黑盒调参。
- 计划：先标注子集（约 0.5-1 人日 / 30 题），扩展 eval/retrieval；当前无数据 → 待补。

#### 6.7.3 幻觉测试（人工回查 + LLM-as-judge）
- 人工回查（已落地）：SOP 见 6.5.4；历史口径真实幻觉 0 例、数字可溯源 99.9%（4068/4071）。
- LLM-as-judge（设计推荐）：
  - judge 输入：问题、生成答案、检索引用（top10 原文）与 SQL 查询结果；
  - 判据（结构化 pass/fail + 原因）：① 关键数值能否在引用 / SQL 结果中找到（口径一致）；② 观点是否基于引用而非模型记忆；③ 公司-数值配对是否错位（呼应历史行序错位缺陷）；④ 合理拒答 / 澄清场景不计为失败；
  - 校准流程：judge 先与人工双回查跑 50 条对齐（一致率 ≥90% 才启用），不一致样本回流优化 judge 提示词；
  - 节奏：P0 人工 SOP → P1 规则 + judge 半自动 → P2 全量门禁。

#### 6.7.4 对抗测试（挑战集具体化，设计推荐）
| 类别 | 目标 | 样例形态 | 通过标准 | 计划数量 |

### 7.6 运维要点与真实案例
- 端口约定：宿主 8000 保留本地 uvicorn，容器后端 18000，浏览器统一 8080（曾因连错端口定位到旧服务）；
- 跨平台：Docker Desktop 默认 host.docker.internal，Linux 需 extra_hosts host-gateway（compose 已固定）；
- 大数据不入镜像：.dockerignore + 只读卷挂载语料；数据迁移（qdrant_storage 旧目录整体搬迁）后须核对集合名；
- 会话/缓存持久化：database 卷与本地同源，重启后可恢复（checkpoint + chat_memory）。

# RAG vs 微调：本项目的边界与选择

> 日期：2026-10-18
> 结论先行：**RAG 负责“可引用的研报观点与证据”，SQL/财报库负责“可计算的财务指标与季度实际值”，微调只适合做格式、分类、字段映射等适配层，不能替代事实记忆和引用。**

## 一、问题不是“RAG 还是微调”，而是“哪类问题该走哪条路”

金融问数至少包含四类请求，它们的正确性来源不同：

| 请求类型 | 例子 | 正确性来源 | 首选链路 |
|:--|:--|:--|:--|
| 研报观点/原因 | “机构为什么下调这家公司的评级？” | 研报原文与引用 | RAG |
| 财务指标实际值 | “2025Q3 营业收入是多少？” | 财报/MySQL 的可计算字段 | SQL / 财报库 |
| 排名、聚合、对比 | “医药行业研发费用前 10 名” | 结构化数据与聚合逻辑 | SQL |
| 混合问题 | “结合财报数据和研报观点分析业绩下滑原因” | 两路证据合并 | SQL + RAG，按来源标注 |

如果把四类问题都塞进一个 RAG 链路，会出现两个典型错误：

1. **研报里只有预测值，没有季度实际值**，模型却把预测值当实际值回答；
2. **SQL 已经能算出的数字**，被要求从研报表格里“找一句话”，导致答案依赖不完整的文本证据。

因此，真正要做的不是“让模型记住更多”，而是**先把问题路由到正确的数据源**。

## 二、RAG 与微调的能力边界

| 维度 | RAG | 微调（LoRA/全参） |
|:--|:--|:--|
| 知识更新 | 改索引/改语料即可 | 需要重新构造数据并训练 |
| 事实可追溯 | 可以返回引用与证据 | 参数里没有可点击的来源 |
| 数值正确性 | 取决于检索到的材料，不能保证计算 | 不能保证算术与最新财报一致 |
| 输出格式/风格 | 靠 prompt 约束 | 适合稳定格式、术语、分类 |
| 领域适配 | 靠检索与 prompt | 适合意图路由、SQL 方言、字段映射 |
| 成本 | 索引、embedding、检索、生成 | 标注、训练、评测、版本管理 |
| 主要风险 | 召回缺失、引用不支持 claim | 幻觉内化、知识过期、灾难性遗忘 |

一句话：**RAG 解决“知识从哪里来”，微调解决“模型怎么稳定地做某件事”。** 两者不是替代关系。

## 三、本项目为什么以 RAG + SQL 为主

### 3.1 语料在变化，事实不能写死进参数

项目当前语料：

- 473 篇研报（个股 160 + 行业 313），由 MinerU 解析并进入 Qdrant；
- 1,432 份财报 PDF（1,252 份正式 + 180 份测试），抽取后入 MySQL；
- MySQL 侧为 80 家公司、903 个（公司、年度、报告期）记录 × 4 张财务表。

研报会新增，财报会更新。把事实“记进模型”意味着每次更新都要重新训练，而且无法保证模型记住的是最新值。RAG 只需重建/增量更新索引；SQL 只需更新数据库。

### 3.2 金融问答需要引用，而不是“模型说它对”

研报观点类问题必须能回到原文。项目已有引用构建与 L1 引用核验链路，RAG 的返回结构天然带 `references`；微调模型的输出没有可点击的证据来源。即使微调模型“答得更像”，也无法满足“这句话来自哪篇研报”的审计要求。

### 3.3 数值错误不可接受，SQL 比“读表”更可靠

财报指标、同比、排名、聚合这类问题，正确做法是查询结构化财务库，而不是让模型从一张研报表格里复制数字。SQL 路的优势是：

- 口径明确（字段、期间、单位）；
- 可重复计算；
- 可以加校验与拒答；
- 不依赖某篇研报是否恰好包含该指标。

### 3.4 当前系统已经有“两路”的雏形

`src/prompts/multi_agent.py` 的 supervisor 已把任务拆成：

- `financial`：数值、指标、对比、排名、趋势、占比；
- `research`：观点、原因、行业分析、目标价、评级。

这说明系统设计上已经承认“财务数据”和“研报观点”是两种证据。当前缺的不是再训练一个模型，而是把这条路由做得更确定：**按指标类型、报告期、数据源可用性做硬路由，而不是只靠 LLM 自由拆任务。**

## 四、季度题为什么必须走 SQL/财报路

### 4.1 研报表的期间结构不支持季度实际值

研报表格以年度实际值（`2024A`）和未来预测值（`2025E/2026E`）为主。v6 行级事实实测：

- 全库 `period=2025Q3` 的行事实共 **2,113 条**；
- 指标以 `收入(YOY)`、`归母净利润(YOY)`、PE、市值等为主；
- `2025Q3 + 营业收入`、`2025Q3 + 研发费用`、`2025Q3 + 投资活动现金流量净额` 的精确匹配均为 **0 条**。

这不是检索代码漏召回，而是**研报语料本身没有这些季度实际值**。继续在研报表里硬找，只会得到“收入同比”或预测值，再把它们误当实际值。

### 4.2 四类问题的路由规则

建议把路由写成可执行的判定，而不是一段模糊的 prompt：

| 判定 | 动作 |
|:--|:--|
| 问题含明确季度（`2025Q3` 等）+ 财务指标 | 先走 SQL/财报库；查不到时明确拒答或说明数据边界 |
| 问题含“预测/目标价/评级/观点/原因” | 走 RAG 研报检索，输出引用 |
| 问题含排名/聚合/多公司对比 | 走 SQL；需要解释时再检索研报观点 |
| 问题同时含数值与观点 | 两路并行，最终答案按 `[财务数据]` / `[研报观点]` 标来源，禁止把预测值写成实际值 |
| 问题只有公司名、没有指标/期间 | 先澄清，不直接猜数据源 |

### 4.3 “Router Data Skill” 的准确定位

本项目当前的 supervisor 是 **LLM 任务拆分**，不是确定性数据路由。`Router Data Skill` 应被定义为一个**计划中的能力**：

- 输入：问题、实体、期间、指标、数据源可用性；
- 输出：`sql` / `rag` / `hybrid` / `clarify`；
- 约束：季度实际值不得路由到研报表；研报预测值必须标注为预测；SQL 查不到时不得用研报文本补成“实际值”。

在它落地前，文档和面试口径只能写“已有 financial/research 两路拆分”，不能写“已完成确定性 Router”。

## 五、微调适合做什么

微调不是没有价值，而是应该放在正确的位置：

| 场景 | 是否适合微调 | 说明 |
|:--|:--|:--|
| SQL 生成/字段映射 | ✅ 适合 | 固定 schema、字段别名、方言约束明确，可用 LoRA 提升稳定性 |
| 意图分类/路由 | ✅ 适合 | 输入短、标签稳定，可作为 Router 的分类器 |
| 财务文本分类/抽取 | ✅ 适合 | 有标注数据时，比长 prompt 更稳定 |
| 研报观点事实记忆 | ❌ 不适合 | 知识会变，且无法引用 |
| 最新财务数值 | ❌ 不适合 | 应查数据库，不应让参数记忆 |
| 替代引用与审计 | ❌ 不适合 | 微调输出没有来源 |

本项目目前的 SQL 生成主要靠 `src/prompts/financial.py` + 校验守卫，没有 LoRA 实验。因此：

- 不能写“已做 LoRA 微调”；
- 不能写“微调后 SQL 准确率提升 X%”；
- 只能写“微调是后续可选的适配层，优先级低于 Router 与数据契约”。

## 六、为什么现在不做“用微调替代 RAG”

1. **没有标注数据**：要做事实型微调，需要大量“问题—答案—证据”样本；当前没有这类训练集。
2. **无法引用**：微调模型不能返回研报文件名、段落或表格坐标，和项目的证据链目标冲突。
3. **更新成本高**：研报与财报持续变化，重训频率不可接受。
4. **评测成本高**：需要证明微调没有把旧知识、错误数值或风格偏好内化；当前评测体系还没有覆盖这类风险。
5. **收益不确定**：项目当前的主要瓶颈是召回覆盖、季度题路由和表级 gold，不是“模型不会说金融话”。

## 七、推荐组合

```text
用户问题
  → 实体/期间/指标解析
  → Router（确定性规则优先，LLM 兜底）
      ├─ SQL/财报库：季度实际值、排名、聚合、对比
      ├─ RAG：研报观点、原因、评级、目标价
      └─ Hybrid：两路并行，按来源标注
  → 答案生成
  → 引用/证据校验（RAG claim 回到研报；SQL 数字回到查询结果）
```

微调在这个组合里的位置：

- 训练 Router 的分类器；
- 训练 SQL 生成/字段映射；
- 训练固定格式的抽取器；
- **不训练事实答案本身**。

## 八、边界与下一步

### 8.1 已成立的事实

- 473 篇研报 + 1,432 份财报 PDF 的双语料结构成立；
- supervisor 已有 financial/research 两路拆分；
- 研报表季度实际值缺失，`2025Q3 + 营业收入/研发费用/投资活动现金流量净额` 精确匹配为 0；
- RAG 的引用链路与 SQL 的财务查询链路都已存在。

### 8.2 尚未成立的事实

- 没有确定性 Router 的实现与评测；
- 没有微调/LoRA 实验；
- 没有“RAG vs 微调”的同任务 A/B；
- 没有证明微调能提升事实正确率；
- 没有表级 gold 支撑“行级证据已可用”。

### 8.3 下一步优先级

1. **先做 Router 规则**：季度实际值、排名/聚合、研报观点、混合问题四类分流；
2. **再做季度题验证**：用 SQL 结果对照研报预测，确认答案不会把 `2025E` 写成 `2025Q3`；
3. **最后评估微调**：只评估 SQL 生成/意图分类等适配任务，不把微调当事实层。
